모델의 답변이 틀렸을 때 확인할 곳은 여러 군데다. 질문에 필요한 문서가 입력에 있었는지, 답변의 어떤 부분을 검사했는지, 같은 실패를 몇 번 반복했는지를 보면 수정할 위치가 드러난다. 모델을 고정해 두고 주변 구성을 바꾸는 실습을 이런 관점에서 정리했다.

## 프롬프트와 컨텍스트와 하네스와 루프

Prompt(프롬프트)에는 수행할 목표와 조건을 적는다. Context(컨텍스트)는 모델에 전달하는 지침, 질문, 문서, 대화 기록을 아우른다. Harness(하네스)는 모델 호출 주변에서 입력 준비, 도구 실행, 검사와 기록을 연결하는 코드와 환경이다. Loop(루프)는 실행 결과를 다음 입력에 반영하고 계속할지 멈출지 결정한다.

| 역할 | 확인할 질문 | 바꿀 수 있는 부분 |
|---|---|---|
| 프롬프트 | 무엇을 어떤 조건으로 작성하는가? | 목표, 제약, 출력 형식 |
| 컨텍스트 | 지금 답변에 필요한 근거가 들어 있는가? | 문서 선택, 배치, 대화 기록 |
| 하네스 | 실행과 검사를 무엇이 담당하는가? | 도구, 권한, 검사 함수, 로그 |
| 루프 | 다음 시도를 할지 무엇으로 결정하는가? | 피드백, 종료 조건, 진행 상태 |

이 구분은 문제를 나누어 보는 관점이다. 넓은 의미의 하네스 안에는 컨텍스트 관리와 루프도 들어간다. 예를 들어 진행 기록을 파일에 저장하고 다음 입력에는 일부만 넣는 함수는 상태 관리와 입력 구성을 함께 맡는다.

RAG(검색 증강 생성)의 검색과 리랭킹도 이 관점에서는 컨텍스트를 고르는 작업이다. 검색이 정확했는데 답변이 틀렸다면 최종 입력에 어떤 문서가 어떤 순서로 들어갔는지, 필요한 조건이 요약 중에 빠졌는지까지 살펴볼 수 있다.

## 모델에 도착하는 입력

실습의 `messages`는 `role`과 `content`를 가진 항목의 목록이다. Chat template(대화 형식 틀)은 이 목록을 모델이 학습한 대화 형식으로 변환한다. 역할 구분자와 발화의 시작·종료 표시가 모델마다 다르므로 모델 교체 후에는 실제 변환 결과도 확인한다.

`apply_chat_template(..., tokenize=False)`는 읽을 수 있는 문자열을 돌려준다. `tokenize=True`는 token ID(토큰 ID)를 얻는 설정이다. `add_generation_prompt=True`는 이를 지원하는 템플릿에서 다음 `assistant` 응답의 시작 표시를 붙인다. 구체적인 효과는 모델의 템플릿에 달려 있다.

문자열로 변환한 뒤 다시 토큰화할 때에는 특수 토큰 중복을 주의한다. Hugging Face는 이 경로에서 `add_special_tokens=False`를 사용하도록 안내한다. 한 번에 토큰화하는 경로와 문자열을 확인하는 경로를 나눠 읽으면 각 설정의 역할이 분명해진다. [Hugging Face Chat templates](https://huggingface.co/docs/transformers/chat_templating)

제공된 노트북은 기본적으로 Qwen2.5-7B-Instruct를 4bit(4비트)로 불러와 로컬 GPU에서 실행한다. `BACKEND="endpoint"`는 별도로 준비한 추론 서버를 사용하는 선택 경로다. 공통 `chat()`은 답변 문자열을 반환하지만 일부 셀은 로컬 모델 객체와 CUDA를 직접 참조한다. 전체 실습의 기준 환경은 로컬 GPU 경로다.

## 토큰 수와 정보 활용은 따로 본다

Context window(컨텍스트 윈도우)에 입력을 구성할 때는 답변 생성에 필요한 공간까지 고려한다. 시스템 지침, 도구 설명, 문서, 이전 대화, 질문의 토큰 수를 나누어 보면 비용이 큰 부분을 찾기 쉽다.

실습의 토큰 표는 문자열을 각각 세어 더한 근사치다. 메시지의 역할 구분자, 문서 사이 줄바꿈, 생성 시작 표시를 포함한 실제 입력 총량과 차이가 있을 수 있다. 표에서 계산한 `TOOLS_DEF`와 `history`도 뒤의 간단한 `rag_answer()`에는 전달되지 않는다. 예산 표의 구성과 실제 함수의 입력을 각각 확인해야 한다.

입력이 한도 안에 들어간 뒤에는 필요한 정보를 잘 활용하는지 평가한다. Attention budget(어텐션 예산)은 긴 입력을 처리할 때의 정보 활용 한계를 설명하는 표현이다. 별도의 숫자 계기로 남은 양을 확인하는 개념으로 다루기보다, 입력을 바꾸었을 때 답변이 어떻게 달라지는지 측정하는 편이 실용적이다. [Anthropic의 컨텍스트 설계 설명](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

Context rot(컨텍스트 로트) 연구는 입력 길이가 늘어날 때 모델이 정보를 사용하는 성능을 살핀다. 질문별 편차가 있을 수 있으므로 평균 점수와 실패 사례를 함께 본다. 긴 입력에서 무조건 일정한 비율로 성능이 떨어진다고 가정할 필요는 없다. [Chroma의 실험](https://www.trychroma.com/research/context-rot)

## 문서를 줄일 때 빠지는 근거

`top-k`는 보통 순위가 있는 검색 후보에서 몇 개를 선택할지 정한다. 제공된 작은 예제의 `chunks[:k]`는 목록의 앞부분을 자른다. 함수 안에는 질문과의 관련도를 계산하는 검색이나 Reranking(재순위화)이 들어 있지 않다.

`k`를 줄이면 토큰은 줄어들지만 문서 뒤쪽에 있던 정답 조항도 빠질 수 있다. 토큰 절감과 근거 보존을 함께 확인해야 한다. 전체 문서의 항목을 빠짐없이 정리하는 작업이라면 일부만 선택하는 방식이 요청의 범위를 충족하는지도 살핀다.

컨텍스트를 관리하는 방법을 동작으로 나누면 선택이 쉬워진다.

| 방법 | 하는 일 | 확인할 점 |
|---|---|---|
| 선별 | 지금 필요한 자료를 고른다. | 빠진 자료에 필수 근거가 있는가? |
| Just-in-time retrieval(필요할 때 검색) | 식별자를 두고 필요한 순간에 내용을 읽는다. | 필요한 자료를 찾고 다시 읽을 수 있는가? |
| Note-taking(외부 기록) | 진행 상황을 파일에 보관한다. | 어떤 기록을 다음 입력으로 가져오는가? |
| 요약·압축 | 긴 자료를 짧은 표현으로 바꾼다. | 조건과 숫자, 예외가 보존되는가? |

어떤 방식을 쓰든 다음 판단에 필요한 정보가 빠질 가능성을 살핀다. 원문과 위치를 보관하면 누락을 발견했을 때 돌아가 확인하기 쉽다.

## 같은 문서의 위치를 바꾸는 실험

Lost in the middle(중간 소실)은 긴 입력 중간에 있는 정보를 충분히 활용하지 못하는 현상이다. 관련 연구는 다중 문서 질문과 정보 검색 과제에서 근거의 위치에 따라 성능이 달라지는 경향을 보고했다. 현재 모델의 유리한 위치는 사용하는 문서와 질문으로 다시 확인한다. [Lost in the Middle 논문](https://arxiv.org/abs/2307.03172)

실습은 정답 문서와 비슷한 주제의 방해 문서를 만들고 정답을 앞·중간·뒤에 놓는다. 기본 설정의 `N_FILLER=100`은 방해 문서 수이고 `PROBE_TRIALS=5`는 위치별 생성 횟수다. 앞의 값은 입력 길이, 뒤의 값은 측정 비율에 영향을 준다. 다섯 번 중 한 번의 차이는 20퍼센트포인트다.

평가 함수 `is_hit()`은 지정한 두 표현이 답변에 함께 있는지 검사한다. 두 표현이 들어간 문장이 근거를 올바르게 설명했는지까지 확인하려면 답변을 읽어야 한다. **이 점수는 지정 문자열의 포함 여부를 측정한다.**

질문과 지시를 끝부분에 다시 두는 배치도 비교한다. 특정 길이나 위치에서 반드시 같은 결과가 나온다고 가정하지 않고 입력 토큰 수, 생성 설정, 실제 답변을 함께 기록한다.

## 가이드는 생성 전에, 센서는 생성 뒤에

Guide(가이드)는 모델이 답을 만들기 전에 읽는 작성 지침이다. Sensor(센서)는 생성된 답을 검사하고 판정과 문제점을 돌려준다. 지침과 피드백을 구분하면 어떤 조건이 생성에 영향을 주었는지 볼 수 있다. [Birgitta Böckeler의 하네스 설계 설명](https://martinfowler.com/articles/harness-engineering.html)

예를 들어 다음은 설명을 위해 만든 장비 대여 규정이다.

> 장비 대여는 3일이며, 담당자의 승인을 받으면 한 번에 한해 2일 연장할 수 있다.

가이드에는 대여 기간과 연장 조건을 함께 적도록 요청한다. 센서는 필수 항목이나 근거 표시를 검사하도록 만든다. 답변에 `3일`이라는 글자가 있어도 연장 횟수와 승인 조건을 제대로 설명했는지는 추가로 확인한다.

계산형 센서는 정규식, 자료형 검사, 테스트 같은 코드로 판정한다. 추론형 센서는 모델에게 근거와 답변을 주고 판정하게 한다. 계산형 센서도 정답 데이터와 비교하도록 구현하면 내용의 일부를 확인할 수 있다. 검사 방식의 이름과 실제로 확인하는 조건을 함께 본다.

## 검사 함수에도 시험용 답변이 필요하다

자료에 없는 질문에는 확인이 필요하다고 답하도록 해 놓고 모든 답변에 조항 번호를 요구하면 규칙이 충돌한다. 모델은 올바른 답변을 하고도 같은 위반을 반복해서 받는다.

센서를 만들 때 통과해야 할 답변과 실패해야 할 답변을 작게 준비한다. 문장 수의 경계, 필수 항목의 누락, 인용을 생략하는 예외를 넣으면 검사 자체의 오류를 찾기 쉽다.

제공된 `check_answer()`는 문장 수, 조항 번호 형태, 일부 존댓말 표현을 확인한다. `check_strict()`는 시작 문구와 끝의 근거 형식 등 다른 조건을 검사한다. 이름이 더 엄격해도 기존의 모든 검사가 포함됐는지는 함수 본문에서 확인한다. 실제로 `check_strict()`에는 기본 센서의 존댓말 검사가 그대로 들어 있지 않다.

## 형식 검사 통과가 뜻하는 범위

정리본의 저장 기록에는 연습용 규정의 일수를 틀리게 답하고도 `pass=True`가 나온 사례가 있다. 해당 함수가 확인한 문장 형식과 근거 표시를 맞췄기 때문이다. 이 기록에서는 **센서가 확인하는 항목 밖의 오류가 통과할 수 있다**는 사실을 확인한다.

LLM-as-a-judge(모델을 이용한 판정)는 규정과 질문, 답변을 함께 주고 사실 일치와 조건 누락을 평가하도록 요청한다. 같은 답변을 규칙 검사와 모델 판정에 넣으면 두 방식이 발견하는 문제를 비교할 수 있다. 답변 모델과 판정 모델이 같다면 같은 실수를 공유할 가능성도 살핀다.

실습의 `judge_sensor()`는 JSON(구조화 데이터)을 찾지 못하거나 Parsing(해석)에 실패하면 `pass=False`를 반환한다. JSON을 읽은 뒤 내부의 `pass`가 불리언인지, `issues`가 목록인지까지 모두 검사하는 코드는 포함되어 있지 않다. 판정 형식의 정상 여부와 판정 내용의 타당성은 각각 확인할 항목이다.

예시 답변에 붙은 ‘내용 O’ 같은 표기도 원문과 대조한다. 일부 예시는 승인자와 일수를 맞췄어도 사용 기한을 빠뜨렸다. 모델의 판정까지 포함해 평가 기준이 어떤 누락을 놓치는지 살펴본다.

## 가이드와 피드백의 차이를 비교한다

실습의 세 조건은 추가 가이드 없이 한 번 생성, 가이드를 주고 한 번 생성, 가이드와 검사 피드백을 주며 재시도하는 방식이다. 결과는 같은 검사 함수로 평가한다.

첫 조건에도 기본 시스템 지침은 있다. 또 앞의 두 조건에서도 생성한 답변의 성적을 계산할 때 센서를 사용한다. 조건 간 차이는 추가 작성 규약과 **생성 과정에 검사 피드백을 넣는지**다.

`answer_with_sensor(q, max_retry=3)`의 3은 첫 생성을 포함한 최대 횟수다. 통과하면 즉시 반환하고, 실패하면 답변과 구체적인 위반 목록을 메시지에 추가한다. 다음 호출은 수정할 부분을 포함한 새로운 입력을 받는다.

비교할 값은 통과율과 평균 생성 횟수다. 통과율을 읽을 때에는 검사한 항목의 범위도 함께 적는다. 문장 수와 근거 표시를 검사했다면 그 점수를 사실 정확도 전체로 부를 수는 없다.

## 멈추는 조건을 값으로 남긴다

반복 횟수, 누적 토큰, 경과 시간은 각각 다른 비용을 제한한다. 간단한 조회와 여러 자료를 비교하는 작업에 필요한 예산도 다르다. 개발자가 상한을 두고 실제 사용량과 종료 이유를 기록해야 한다.

| 종료 이유 | 판단 기준의 예 |
|---|---|
| 성공 | 필요한 검사를 통과했다. |
| 한계 | 허용한 생성 횟수나 토큰·시간을 소진했다. |
| 정체 | 정한 기간 동안 같은 위반이 반복됐다. |
| 위임 | 사람의 판단이나 별도 권한이 필요하다. |

기본 루프는 성공과 반복 상한을 확인한다. `loop_with_stall()`은 직전과 현재의 `issues` 목록이 같으면 정체로 반환한다. 목록의 내용과 순서가 같아야 하며, 다른 오류가 번갈아 발생하는 상황은 이 조건으로 잡지 못한다.

다음은 종료 판정만 떼어 새로 작성한 작은 예제다. `attempts`는 이미 수행한 생성 횟수이고 `max_attempts`는 1 이상인 최대 횟수다. 외부 모델 호출은 없으며 네 경로를 정해진 값으로 확인했다.

```python
def next_step(passed, issues, previous, attempts, max_attempts):
    if passed:
        return "성공"
    if previous is not None and issues == previous:
        return "정체"
    if attempts >= max_attempts:
        return "한계"
    return "다시 시도"

print(next_step(False, ["근거 누락"], ["근거 누락"], 2, 4))
# 정체
```

함수는 성공, 정체, 한계 순으로 검사한다. 마지막 허용 시도에서 같은 위반이 반복되면 `정체`가 기록된다. 종료 이유가 겹칠 때 무엇을 우선할지도 코드의 일부다.

정체는 검사 목록이 반복됐다는 신호다. 다음 시도의 실패까지 확정하지는 않는다. 너무 빨리 끝내는 기준은 나중에 성공할 요청을 놓칠 수 있다. 정체한 답변을 모아 지침 충돌, 센서 오류, 근거 부족을 살펴본다. 노트북은 정체한 질문을 출력하며, 사람에게 알림을 보내거나 배정하는 동작은 별도로 구현해야 한다.

## 저장된 반복 결과의 해석

제공된 정리본은 이전 실행 출력을 보존했다고 밝히고 있다. 저장 기록에서는 최대 1회일 때 통과율 80%, 2회부터 100%가 표시되며 2회 이상에서 평균 시도는 1.2회다. 통과한 질문이 즉시 종료되므로 상한을 늘렸다고 항상 호출 수가 늘지는 않는다.

정체 종료를 추가한 비교는 두 방식 모두 통과율 100%, 총 6회 호출이었다. 해당 기록에서는 호출 절감 효과가 관찰되지 않았다. 효과가 있을 것이라는 설계 의도와 실제 측정값을 나누어 읽는다.

이 값은 작은 평가 세트의 저장된 출력이다. 이번 글을 작성하며 GPU에서 새로 얻은 성능 수치가 아니다. 모델이나 라이브러리, 생성 조건이 달라지면 다시 측정해야 한다.

## 컴팩션에서 남길 기록

Compaction(누적 기록 압축)은 다음 작업에 필요한 정보로 대화와 실행 기록을 줄이는 과정이다. 실습의 `loop_with_compaction()`은 이전 답변 전문 대신 중복을 제거한 위반 목록을 다음 입력에 넣는다.

이때 기존 규정과 질문은 유지한다. 과거 위반은 누적되므로 이미 해결한 항목도 남을 수 있다. 상태가 길어지면 현재 해결되지 않은 문제와 과거의 주의 사항을 구분하는 방식도 생각할 수 있다.

무엇을 남길지는 다음 행동을 바꾸는지로 판단한다. 파일 경로를 잘못 읽었다는 오류나 사용할 수 없는 도구라는 정보는 후속 선택에 필요하다. 형식 오류를 반복한 답변 전문은 위반 항목으로 줄일 여지가 있다. 원래 목표, 필수 제약, 근거의 위치는 압축 후에도 확인할 수 있게 둔다.

저장된 컴팩션 실행은 첫 시도에 종료되므로 여러 차례 압축의 누적 효과를 보여 주지 않는다. 대화 전체를 계속 추가한 다른 셀과는 생성 조건과 종료 방식도 달라, 두 셀의 토큰 수를 단순 비교해 절감률을 계산할 수는 없다.

## 선택 실습에서 확인할 동작

다섯 트랙은 앞의 구성을 하나씩 확장한다. 학습 자료의 공유 기준은 이 중 두 트랙을 선택해 바꾼 조건과 결과를 설명하는 것이다.

**진행 기록을 파일로 남기기.** `process_with_notes()`는 질문별 결과를 `progress.json`에 저장하고 다시 실행할 때 이미 기록된 질문을 건너뛴다. 다음 입력에는 최근 3개 답변의 앞 60자만 넣는다. `summary`라는 이름의 값은 문자열을 자른 결과다. 검사에 실패한 질문도 기록되어 있으면 건너뛰며, 파일 해석이 실패하면 빈 기록으로 시작한다. 성공한 작업과 단지 기록된 작업을 구분해 읽는다.

**규칙 검사와 모델 판정 비교하기.** 같은 답변을 두 센서에 넣고 각각 잡은 오류와 놓친 오류를 확인한다. 판정 모델이 조건 누락을 놓쳤다면 그 사례도 함께 남긴다.

**요약 길이와 정보 보존 비교하기.** `compress()`의 `target_ratio`는 원문 글자 수에 곱해 요청하는 목표 길이다. 0.6을 요청했다고 실제 토큰 수가 정확히 60%가 되지는 않는다. 평가 표는 4개 질문의 `key in ans`로 키워드 포함률을 계산하고 자료에 없는 질문은 제외한다. 기본 구성에서는 요약 12회와 답변 12회, 총 24번의 모델 호출이 필요하다. 요약을 생성하는 비용도 함께 본다.

**질문을 나누고 답변을 종합하기.** `subagent_answer()`는 같은 `chat()`을 호출하면서 하위 질문마다 별도 메시지 목록을 만든다. `for`문으로 순서대로 처리하며 하위 질문이 n개면 분해 1회, 개별 답변 n회, 종합 1회로 총 n+2회 호출한다. 종합 단계에는 규정 원문 없이 하위 답변만 전달한다. 앞 단계의 조건 누락이 최종 답변에도 남을 수 있다. 단일 호출과의 비교에서는 생성 설정 차이도 고려한다. 제공된 종합 호출은 기본 `temperature=0.2`, 단일 호출은 `0.0`이다.

**고정 입력의 배치 비교하기.** Prefix cache(입력 접두부 캐시)는 같은 입력 앞부분의 계산을 재사용한다. 지원하고 활성화한 서버에서는 고정 지침과 공통 자료를 앞에 두는 구성이 유리할 수 있다. [Manus의 캐시 설계 기록](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

현재 로컬 `chat()`에는 호출 사이의 캐시를 보관해 다음 호출로 넘기는 코드가 없다. `timed_run()`의 두 배치는 질문의 위치와 메시지 역할도 바꾼다. 측정한 시간에는 출력 길이, 실행 순서, GPU 상태 등의 영향이 섞일 수 있다. 서버의 캐시 지원·활성화와 적중량을 확인해야 캐시 효과를 따로 평가할 수 있다.

## 내 작업에 적용할 때

최종 개인 과제는 반복할 작업 하나를 고르고 작성 규칙 5개 이상과 평가 입력 8개 이상을 준비하는 구성이다. 검사 함수부터 작은 정답·오답으로 확인하고 추가 지침 없음, 지침만 제공, 지침과 피드백 제공의 세 조건을 같은 기준으로 비교한다.

최대 생성 횟수 1·2·3·5회에서 통과율과 평균 시도를 기록한다. 실패한 답변과 위반 목록을 읽고 입력 구성, 지침, 검사, 루프 중 바꿀 위치를 설명한다. 높은 점수에서도 무엇을 검사했고 무엇이 남았는지 적으면 다음 실험의 목적이 분명해진다.

모델이 필요한 근거를 받았는지, 검사 결과가 타당했는지, 피드백 뒤에 어떤 변화가 있었는지. 이 세 가지를 기록해 두면 모델 주변의 구성을 구체적으로 고칠 수 있다. 충분한 근거와 올바른 피드백을 주어도 해결되지 않는 과제는 모델 능력과 작업 난이도를 함께 검토한다.

## 자료와 실행 범위

개인 학습 자료의 개념과 구현 흐름을 새로 설명했다. 장비 대여 규정과 종료 판정 함수는 이 글의 설명용 예제다. 종료 판정 함수는 모델 없이 실행해 성공·정체·한계·재시도 경로를 확인했다. 노트북의 저장 출력은 과거 기록으로 구분했으며 모델 다운로드, GPU 추론, 성능 재측정은 수행하지 않았다.

복습 음성은 같은 주제를 24장으로 나누어 입력, 검사, 반복의 역할을 말로 설명한다. 기술 용어와 코드 이름은 영어 발음을 한글로 풀어 읽는다. 파일 자체에 1.1배속을 적용했으므로 플레이어는 1.0배속으로 두면 된다.
