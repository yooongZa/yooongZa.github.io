문서에서 글자를 모두 꺼냈는데도 질문에 답할 수 없는 경우가 있다. 표의 숫자는 남았지만 어느 행과 열의 값인지 알 수 없고, 차트의 제목은 읽었지만 선이 꺾이는 지점은 사라진다. Multimodal RAG(멀티모달 검색 증강 생성)는 이런 문서를 검색과 답변에 활용하는 방법을 다룬다.

문서를 읽는 단계부터 답변이 나오는 단계까지 입력과 출력을 따라 정리했다. 음성은 같은 개념을 듣기 편하게 풀어 설명하고, 본문에는 비교표와 직접 만든 재고 검증 예제를 더했다.

## 1. 값과 관계를 함께 읽기

보고서에 센터별 재고 표가 있다고 해 보자. 봄센터의 1월 재고는 120개, 2월 재고는 145개다. 이 숫자는 설명을 위해 만든 값이다. `봄센터 120 145`라는 문자열만 남기면 각 숫자의 기준 시점과 단위가 불분명하다. `센터=봄, 기준월=2월, 지표=재고, 단위=개, 값=145`처럼 관계가 유지되어야 특정 질문의 근거로 쓸 수 있다.

차트는 축, 단위, 범례, 선과 막대의 모양을 함께 봐야 한다. ‘2월에 재고가 증가했는가’는 추세를 확인하는 질문이고, ‘정확히 몇 개 증가했는가’는 수치가 필요한 질문이다. 같은 이미지라도 질문에 따라 필요한 정보가 다르다.

문서가 답변으로 이어지는 경로는 `원본 → 추출한 내용 → 검색 표현 → 선택한 근거 → 답변`으로 나눠 볼 수 있다. 결과가 틀리면 어느 단계까지 정보가 보존됐는지 확인한다. 누락된 페이지를 찾는 문제와 찾은 페이지의 숫자를 읽는 문제는 수정할 위치가 다르다.

## 2. PDF를 문자열로 바꾸는 과정

PDF는 화면과 인쇄물의 배치를 유지하는 데 적합하다. 많은 파일에서 글자의 위치를 바탕으로 문단과 표를 복원해야 한다. Tagged PDF(태그가 있는 PDF)는 구조 정보를 담을 수 있지만, 파일마다 제공하는 구조의 수준이 다르다.

두 단으로 편집한 문서를 한 줄씩 좌우로 이어 읽으면 서로 다른 문단이 섞인다. 머리글과 쪽번호가 본문 중간에 들어가는 경우도 있다. Reading order(읽는 순서)를 확인해야 하는 까닭이다. 글자 일치율이 높아도 문장 순서나 표의 행·열 연결이 틀리면 질문에 필요한 의미가 달라진다.

스캔 페이지에는 일반 텍스트 추출기로 읽을 문자 계층이 없을 수 있다. OCR(광학 문자 인식)을 수행하면 문자를 얻을 수 있고, 문서 파서는 여기에 레이아웃 분석과 표 복원 등을 조합한다. 도구가 ‘OCR을 지원한다’는 말만 확인하기보다 실제 출력에 텍스트, 위치, 표 구조가 어떻게 들어가는지 살펴본다. [Docling의 문서 처리 기능](https://docling-project.github.io/docling/)

## 3. 문서 파서와 VLM의 역할

Parser(파서)는 파일을 읽어 프로그램에서 다룰 내용을 꺼낸다. OCR, 표 인식, 레이아웃 분석을 단계별로 연결할 수도 있고, VLM(Vision Language Model, 시각 언어 모델)에 페이지를 보여 주고 설명이나 구조화된 결과를 생성하게 할 수도 있다.

선택할 때는 문서의 형태와 필요한 출력을 먼저 정한다. 깨끗한 디지털 산문, 작은 글자가 빽빽한 표, 흐린 스캔, 화살표가 많은 도면은 처리 조건이 다르다. 한국어 문서라면 작은 한글, 다단 머리글, 세로 글씨, 도장과 겹친 글자도 평가 자료에 포함한다.

VLM의 출력은 매끄럽게 끝나도 원본을 빠뜨릴 수 있다. 10행 중 9행만 옮기거나, 인접한 두 값을 바꾸거나, 같은 행을 반복할 수 있다. 행 수·열 수·항목 이름·단위·수치를 원본과 대조한다. JSON 문법 검사에 성공했다는 사실은 프로그램이 출력을 해석할 수 있다는 뜻이다. 내용의 정확성은 별도의 검사로 확인한다.

도구를 운영에 적용할 때는 해당 버전의 코드와 모델 가중치의 사용 조건을 각각 확인한다. 문서가 로컬에서 처리되는지, 외부 서비스에 전송되는지도 구분한다. 다운로드 가능 여부만으로 사용 조건을 판단하기는 어렵다.

## 4. 이미지에서 답변 문자열까지

대표적인 VLM 구조는 Vision Encoder(비전 인코더)가 이미지의 특징을 만들고, Projector(투영 계층) 등의 연결 장치가 그 특징을 언어 모델이 사용할 형태로 맞추는 방식으로 이해할 수 있다. 구체적인 결합 방식은 모델마다 다르다.

Hugging Face의 Qwen3-VL 사용 흐름에서는 이미지와 질문을 메시지로 구성하고, 프로세서가 모델 입력을 준비한 뒤 `generate()`로 답변을 생성한다. 생성 결과의 입력 부분을 제외한 뒤 디코딩하면 답변 문자열을 얻는다. [Qwen3-VL 공식 사용 문서](https://huggingface.co/docs/transformers/model_doc/qwen3_vl)

| 단계 | 들어오는 것 | 나가는 것 |
|---|---|---|
| 메시지 구성 | 이미지와 질문 | 역할·내용을 가진 메시지 목록 |
| 프로세서 | 메시지·이미지 | token ID(토큰 ID), 이미지 입력 등 |
| 모델 생성 | 준비된 입력 묶음 | 생성된 토큰 |
| 디코딩 | 답변에 해당하는 토큰 | 답변 문자열 |

코드를 읽을 때 `processor`와 `model`의 역할을 구분하면 편하다. 프로세서는 입력을 준비하고 모델은 그 입력을 받아 생성한다. `def`로 함수를 정의한 뒤 실제 질문을 넣어 호출할 때 이 처리가 실행된다.

## 5. 해상도와 토큰 예산

이미지는 모델 안에서 여러 토큰에 해당하는 자리를 차지한다. 한 토큰에 대응하는 블록의 한 변을 32픽셀로 가정하면 640×640 이미지는 단순 계산으로 `20 × 20 = 400`개의 블록이 된다. 실제 입력에서는 크기 조정, 상·하한, 반올림 규칙이 적용되므로 이 숫자는 근사치다.

Qwen3-VL 프로세서 코드는 이미지 격자 크기와 병합 크기를 사용해 이미지 토큰 수를 계산한다. 모델 계열이 바뀌면 계산 방식도 확인해야 한다. [Qwen3-VL 프로세서 구현](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_vl/processing_qwen3_vl.py)

`input_ids.shape[1]`을 출력했다면 이름을 **전체 입력 토큰 수**로 붙인다. 이미지용 토큰뿐 아니라 질문과 채팅 형식의 토큰도 함께 들어 있기 때문이다. 배치가 하나일 때 첫 축은 입력 묶음의 개수, 두 번째 축은 입력 길이를 나타낸다.

해상도를 비교할 때는 같은 표 질문을 고정하고 입력 길이, 답변 결과, 시간을 기록한다. 원본 이미지가 이미 작으면 허용 상한을 높여도 실제 입력 크기가 늘지 않을 수 있다. 현재 문서에서 정확도가 정체되는 구간을 찾고, 작은 글자나 복잡한 도면은 별도로 측정한다.

또한 모델 가중치의 4bit(4비트) 양자화와 이미지 입력의 크기는 다른 설정이다. 가중치 메모리를 줄였어도 입력과 KV cache(키·값 캐시), 생성 과정에 쓸 공간은 필요하다. 이미지 장수와 생성 길이까지 함께 조절한다.

## 6. 네 패턴을 나누는 두 질문

검색에 쓸 표현과 답변 모델에 보여 줄 자료를 각각 정한다. 이 두 질문으로 패턴을 구분하면 이름을 외우는 부담이 줄어든다. 아래 구분은 학습용이며 실제 시스템에서는 조합할 수 있다.

| 패턴 | 검색에 쓰는 표현 | 답변 단계에서 확인할 내용 |
|---|---|---|
| 1. 캡션 활용 | 이미지 설명의 텍스트 벡터 | 캡션과 산문 |
| 2. 단일 벡터 이미지 검색 | 이미지·질문을 공통 공간에 표현 | 설계에 따라 이미지·연결 자료 |
| 3. 검색 후 원본 전달 | 캡션·OCR 등의 텍스트 벡터 | 검색된 원본 이미지와 산문 |
| 4. 페이지 멀티벡터 검색 | 페이지와 질문의 여러 벡터 | 찾은 페이지를 답변 단계로 전달 |

패턴 2와 4는 검색 표현의 차이를 강조한다. 패턴 1과 3은 답변 입력의 차이를 비교하기 좋다. 패턴 4로 찾은 페이지를 VLM에 전달하는 구성도 가능하다. 원본 파일은 어느 방식에서든 별도로 보관할 수 있다.

## 7. 캡션으로 검색하고 답하기

Caption(캡션)은 이미지 내용을 글로 옮긴 설명이다. 패턴 1은 캡션을 만든 뒤 텍스트 검색 경로에 넣는다. 질의 시점의 답변 모델은 검색된 캡션과 산문을 읽는다. VLM 작업을 자료를 준비하는 시점에 모아 둘 수 있다.

캡션에는 질문에 필요한 정보가 남아 있어야 한다. 재고 표를 옮길 때 센터 이름, 월, 수량, 단위를 함께 적고 표의 제목과 근거 페이지를 연결한다. 답변 시점에 원본 이미지를 전달하지 않는 구성에서는 캡션에서 빠진 값을 확인할 경로가 없다. 원본을 보관했다면 다시 읽거나 재색인할 수 있다.

검색용 Embedding(임베딩) 모델은 캡션과 질문을 숫자 벡터로 바꾼다. 학습 예제의 `multilingual-e5-small`은 검색 문서 앞에 `passage: `, 질문 앞에 `query: `를 붙이는 사용 규칙을 갖는다. 정규화한 벡터끼리 내적하면 코사인 유사도를 구할 수 있다. 모델 카드에는 긴 입력의 잘림 조건도 있으므로 긴 캡션을 그대로 넣을 때는 확인이 필요하다. [E5 모델 카드](https://huggingface.co/intfloat/multilingual-e5-small)

검색 함수는 높은 점수의 페이지를 반환하고 답변 함수가 그 내용을 언어 모델에 전달한다. 임베딩 모델과 답변 모델의 출력이 서로 다르다는 점을 구분해 읽는다.

## 8. 찾은 원본을 다시 보여 주기

패턴 3은 텍스트로 후보를 좁힌 뒤 해당 페이지의 원본 이미지를 VLM에 전달한다. 캡션에서 빠진 작은 값을 다시 읽을 기회가 생긴다. 산문 페이지가 함께 검색되면 텍스트도 같이 보낼 수 있다.

함수의 흐름은 `질문 → 검색 결과 → 이미지·산문 분리 → 입력 구성 → 답변`이다. 이미지가 있으면 VLM을 호출하고 산문만 있으면 텍스트 모델을 호출하는 분기를 둘 수 있다. 이미지가 있는 페이지의 캡션을 답변에도 넣을지, 검색에만 쓸지도 명시적으로 정한다.

원본을 전달해도 검색 누락은 남는다. 정답 페이지가 후보에 들지 않았다면 VLM이 그 페이지를 읽을 기회가 없다. 올바른 페이지를 전달한 뒤에도 작은 숫자나 인접한 열을 잘못 읽을 수 있다. ‘검색 성공’과 ‘읽기 성공’을 각각 기록하면 문제를 구분할 수 있다.

이미지를 여러 장 넣으면 필요한 근거도 늘지만 관련 없는 내용과 입력 길이도 늘어난다. 실제 모델 입력에 들어간 페이지 목록을 확인하고, 질문 유형별로 장수를 바꿔 비교한다. 특정 장수를 모든 문서에 적용할 최적값으로 단정하지 않는다.

## 9. 페이지를 여러 벡터로 검색하기

단일 벡터 방식은 이미지 하나를 하나의 벡터로 표현한다. 사진의 전체 모양을 찾는 작업과 빽빽한 표의 특정 항목을 찾는 작업에는 서로 다른 표현이 유리할 수 있다. 실제 자료와 질문으로 비교할 필요가 있다.

ColPali는 페이지 이미지를 여러 벡터로 나타내고 질문의 여러 토큰 벡터와 비교하는 검색 접근이다. Late interaction(늦은 상호작용)의 MaxSim 계산은 질문 토큰마다 페이지에서 가장 잘 맞는 벡터의 유사도를 고른 뒤 그 점수들을 합하는 방식으로 이해할 수 있다. [ColPali 연구진의 설명](https://huggingface.co/blog/manu/colpali)

저장량의 기본 계산은 다음과 같다.

```text
페이지 수 × 페이지당 벡터 수 × 벡터 차원 × 값 하나의 바이트 수
```

이 값에 검색 색인, 페이지 메타데이터, 원본 이미지 등이 더해진다. 페이지의 부분별 대응을 살펴보는 만큼 저장과 점수 계산의 부담도 고려한다. 벡터 압축, 여러 벡터를 묶는 Pooling(풀링), 후보를 먼저 줄인 뒤 정밀하게 점수를 매기는 방법은 속도와 품질을 같이 측정한다.

벡터 데이터베이스를 고를 때는 여러 벡터를 저장할 수 있는지에 더해, 그 표현으로 후보 검색과 재순위 계산을 어떻게 수행하는지 확인한다. 기능 이름이 같아도 실제 검색 경로와 제약은 다를 수 있다.

## 10. 표를 검색할 때와 계산할 때

행을 검색 단위로 나눌 때는 각 행에 표 제목, 열 제목, 단위를 붙인다. 특정 센터의 재고를 묻는 질문에는 행별 표현을 활용할 수 있다. 전체 합계나 여러 센터를 비교하는 질문에는 필요한 행들을 다시 모으는 경로가 필요하다. 병합된 머리글은 상위 제목이 어느 열에 적용되는지까지 보존한다.

표의 합계는 구조화한 숫자로 계산할 수 있다. `표 이미지 → 구조화 출력 → 숫자 검증 → 계산` 순서로 역할을 나눈다. 모델이 잘못 읽은 값이 들어오면 계산식이 맞아도 원본과 다른 답을 얻는다. 합계만 같다고 개별 셀까지 정확한 것도 아니다.

아래는 직접 만든 재고 데이터의 작은 검증 예제다. 예상한 두 센터가 정확히 한 번씩 있고, 재고가 음이 아닌 정수인지 확인한 뒤 더한다. 이미지 인식이나 RAG 검색을 수행하는 코드는 아니다.

```python
def checked_total(rows, expected_centers):
    seen = set()
    total = 0
    for row in rows:
        center = row["center"]
        value = row["stock"]
        if center in seen:
            raise ValueError("센터가 중복되었습니다")
        if type(value) is not int or value < 0:
            raise ValueError("재고는 음이 아닌 정수여야 합니다")
        seen.add(center)
        total += value
    if seen != set(expected_centers):
        raise ValueError("센터가 누락되었거나 추가되었습니다")
    return total


rows = [
    {"center": "봄", "stock": 145},
    {"center": "가을", "stock": 80},
]
print(checked_total(rows, {"봄", "가을"}))  # 225
```

이 검사도 이미지에 적힌 값과 일치하는지는 알 수 없다. 예상 센터와 자료형을 통과한 뒤 원본 셀과 대조하는 과정이 남는다. pandas에서 `errors="coerce"`를 사용하면 변환 실패가 결측값이 되고, 기본 합계 연산이 이를 건너뛸 수 있다는 점도 주의한다. 누락을 확인한 뒤 합계를 계산해야 일부 값만 더한 결과를 완성된 답으로 쓰는 일을 줄일 수 있다.

## 11. 캡션 실험이 실제 검색에 반영되려면

캡션 프롬프트에는 행별 형식, 열 제목, 단위, 누락 점검 조건을 적을 수 있다. 바꾼 프롬프트의 효과를 보려면 같은 이미지로 결과를 비교한다. 원본 값이 캡션 문자열에 몇 개 나타나는지 세는 Coverage(포함률)는 빠르게 누락을 살펴보는 지표다.

단순 문자열 포함은 행·열 대응을 확인하지 않는다. `120`을 찾는 검사는 `1200`도 통과할 수 있고, 서로 뒤바뀐 값들도 모두 포함됐다고 판단할 수 있다. 포함률이 높아졌다면 행별 대조와 실제 질문 평가를 이어 한다.

새 캡션을 생성한 것과 검색 색인을 갱신한 것은 별도다. 실험 변수에 새 문자열을 저장했어도 기존 문서 목록과 벡터가 그대로면 검색은 이전 캡션을 사용한다. `캡션 저장 → 검색 자료 갱신 → 벡터 재생성 → 같은 질문으로 비교`까지 연결한다.

## 12. 질문과 페이지를 분류해 경로 고르기

Router(라우터)는 질문의 종류에 따라 처리 경로를 선택한다. 표의 수치를 원본에서 읽을지, 산문과 캡션으로 설명할지 고르는 실험을 할 수 있다. 숫자를 묻는 질문의 근거가 산문에 있을 수도 있으므로 질문의 표현과 필요한 자료를 함께 고려한다.

모델로 분류하면 라우팅 자체에도 시간이 든다. 질문당 시간은 분류와 검색, 답변 생성까지 같은 범위로 측정한다. 선택한 경로가 의도한 분류와 맞는지, 최종 답변이 맞는지를 따로 기록한다. 라우터가 올바른 경로를 선택한 경우에도 이후 단계의 오류가 남을 수 있다.

자료를 준비하는 단계에서는 페이지를 분류할 수 있다. 디지털 텍스트가 충분한 산문은 직접 추출하고, 스캔이나 중요한 시각 자료가 있는 페이지를 VLM에 보내는 식이다. 글자 수와 이미지 개수만 사용하는 간단한 규칙은 로고나 복잡한 PDF 구성에 영향을 받는다. 호출 횟수와 함께 정보 보존 여부를 확인한다.

3페이지 중 2페이지에 모델을 호출했다면 전수 처리 대비 호출 비율은 약 67%, 줄인 호출의 비율은 약 33%다. 호출 수가 줄어든 비율과 실제 시간·비용이 줄어든 비율은 각각 측정해야 한다.

## 13. 점수와 비용을 무엇으로 계산했는가

학습 코드에서 ‘정확도’라고 출력하더라도 실제 계산식은 정답 키워드 포함률일 수 있다. `any(key in answer for key in keys)`는 후보 중 하나만 들어가면 통과한다. 오답 문장에 정답 단어가 들어가도 통과할 수 있어 사실 정확도와 구분한다.

평가를 나눠 보면 어느 단계가 실패했는지 알기 쉽다.

| 확인할 단계 | 질문 |
|---|---|
| 추출 | 원본의 값·구조가 검색 자료에 남았는가? |
| 검색 | 정답 페이지가 상위 후보에 들어왔는가? |
| 입력 구성 | 그 근거가 실제 모델 입력에 전달됐는가? |
| 답변 | 수치·단위·설명이 근거와 일치하는가? |
| 계산 | 검증된 숫자에 올바른 연산을 적용했는가? |

수치, 추세, 산문 질문을 나눠 맞은 수와 전체 문항 수를 기록한다. 작은 질문 세트에서는 한 문항의 영향이 크다. 추론의 무작위성, 검색 개수, 해상도, 생성 길이, 실행 환경도 결과에 영향을 줄 수 있다. 제공 자료의 저장 결과와 지금 새로 실행한 결과를 구분해 남긴다.

비용은 처음 자료를 색인하는 작업, 저장·검색, 질문마다 답하는 작업으로 나눠 계산한다. 변경된 문서를 다시 처리하는 비용도 포함한다. 외부 사례의 페이지당 가격이나 지연을 자신의 환경에 그대로 적용하기보다 문서 수, 갱신량, 질의 수, 사용 모델을 기준으로 추정한다.

## 14. 구현 흐름과 확인한 범위

실습은 텍스트 추출의 한계를 확인하고, 이미지 모델을 준비한 뒤 캡션 검색과 원본 이미지 답변을 비교하는 흐름이다. 이어 질문 라우팅, 해상도, 캡션 프롬프트, 표 구조화, 페이지 분류를 각각 실험한다. 모델이 수행하는 작업과 파이썬 코드가 수행하는 작업을 나누어 읽으면 전체 경로가 보인다.

자유 프로젝트에서는 문서와 질문, 정답, 근거 페이지부터 고정한다. 같은 질문을 텍스트 추출 경로, 캡션 경로, 원본 이미지 경로에 넣고 유형별 결과와 시간을 기록한다. 실패한 질문은 검색 누락, 캡션 손실, 이미지 오독, 답변 생성 오류로 나눠 원본과 대조한다.

이 글의 재고 검증 예제는 로컬에서 실행했다. 노트북 개선본은 구조·문법과 모의 모델 호출을 이용한 간이 검사를 수행했다. GPU 추론, 모델 다운로드, 새 커널 전체 실행과 성능 재측정은 수행하지 않았다. 음성은 이 글과 같은 개념을 복습하는 합성 음성이다.

문제가 생기면 검색된 페이지와 실제 모델 입력부터 기록한다. 그 기록이 있으면 필요한 정보가 어디서 빠졌는지, 전달된 정보를 어느 단계에서 잘못 읽었는지 구분할 수 있다.
