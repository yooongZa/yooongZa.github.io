제일장. 모델을 고를 때 적어 둘 조건

사내 문서에 답하는 인공지능을 만든다고 생각해 봅시다. 모델 이름을 고르기 전에 문서가 어디로 전송되는지, 회사에서 어떤 용도로 쓸지, 동시에 몇 건을 처리할지부터 적습니다. 같은 모델도 혼자 짧게 질문할 때와 여러 사람이 긴 계약서를 넣을 때 필요한 자원이 달라집니다.

이번 복습은 모델의 공개 방식, 메모리, 퀀타이제이션, 라이선스, 비용, 평가 순서로 이어집니다. 마지막에는 후보를 선택한 이유와 다시 검토할 조건까지 남깁니다. 모델 순위는 바뀌어도 이 기록은 다음 선택에 쓸 수 있습니다. 실제 모델을 실행해 얻은 성능 수치는 다루지 않으며 계산에 등장하는 가정은 따로 설명하겠습니다.

제이장. 공개 방식과 실행 장소

오픈 웨이트는 학습된 가중치를 내려받을 수 있다는 뜻입니다. 사용할 수 있는 범위는 해당 모델의 라이선스에서 확인합니다. 오픈소스 에이아이는 사용과 수정, 공유의 자유뿐 아니라 데이터 정보와 코드, 파라미터를 함께 살피는 개념입니다. 가중치 공개라는 한 조건으로 모든 사용 권한이 정해지지는 않습니다.

실행 장소도 따로 적어야 합니다. 같은 공개 모델을 회사 서버에 올릴 수도 있고 외부 업체의 에이피아이로 이용할 수도 있습니다. 외부에서 추론하면 그 업체로 요청 내용이 전송됩니다. 자체 서버를 쓰더라도 검색, 로그, 모니터링 같은 다른 경로에서 데이터가 나갈 수 있어 전체 요청 경로를 확인합니다. 모델의 공개 방식과 데이터의 이동 경로를 두 칸으로 나누면 혼동이 줄어듭니다.

제삼장. 계열 이름보다 정확한 모델 버전

큐웬, 라마, 젬마, 미스트랄, 딥시크처럼 여러 모델 계열이 있습니다. 한국어 업무를 살필 때는 솔라와 엑사원 같은 계열도 검토할 수 있습니다. 이 이름들은 후보를 찾는 출발점입니다. 선정 기록에는 정확한 저장소 이름과 버전, 확인 날짜를 적습니다.

같은 계열이라도 크기, 입력 종류, 대화 형식, 라이선스가 달라집니다. 베이스 모델은 이어질 내용을 예측하도록 학습한 바탕 모델이고, 인스트럭션 튜닝 모델은 지시를 수행하도록 추가로 조정한 모델입니다. 채팅 서비스에서는 어떤 대화 형식을 기대하는지도 확인합니다. 인기와 다운로드 수는 자료를 찾는 데 참고할 수 있지만 우리 업무의 정답률은 직접 평가해야 알 수 있습니다.

제사장. 총 파라미터와 활성 파라미터

엠오이는 여러 전문가 모듈 중 일부를 선택해 계산하는 구조입니다. 총 파라미터는 모델 전체의 크기를 가리키고 활성 파라미터는 토큰을 처리할 때 실제 계산에 참여하는 규모를 나타냅니다. 큐웬 삼 점 오의 한 모델은 총 삼천구백칠십억 개, 활성 백칠십억 개의 파라미터로 안내됩니다.

가중치를 모두 지피유에 올리는 구성이라면 메모리는 전체 가중치를 기준으로 계산합니다. 활성 파라미터만 넣으면 필요한 공간을 크게 과소평가합니다. 활성 규모는 계산량을 가늠하는 단서지만 실제 속도에는 메모리 대역폭, 전문가를 고르는 과정, 여러 장치 사이의 통신도 영향을 줍니다. 씨피유로 일부를 옮기는 방식도 가능하나 그때는 이동 비용을 포함해 속도를 측정해야 합니다.

제오장. 한국어 업무를 평가하는 방법

한국어 지원이라는 설명만으로 사내 규정 답변의 품질을 알기는 어렵습니다. 회사에서 실제로 시킬 일을 작은 평가 묶음으로 만듭니다. 요약, 항목 추출, 문의 분류, 근거를 붙인 답변, 정해진 형식의 출력처럼 업무를 나눕니다.

처음에는 스무 건 정도로 실패 유형을 찾아볼 수 있습니다. 숫자와 날짜가 섞인 문장, 부정 표현, 긴 조항, 근거가 부족한 질문을 넣으면 단순 대화에서 드러나지 않던 차이를 볼 수 있습니다. 스무 건은 탐색용 출발점이며 운영 품질을 확정하기에는 자료가 더 필요합니다. 후보에는 같은 조건을 적용하고 가능하면 모델 이름을 가린 채 답을 읽습니다. 점수와 함께 어떻게 틀렸는지도 기록합니다.

제육장. 가중치 메모리의 첫 계산

파라미터 하나를 십육 비트로 저장하면 이 바이트가 필요합니다. 팔 비트는 일 바이트, 사 비트는 영 점 오 바이트입니다. 따라서 파라미터가 팔십억 개라면 이론상 가중치는 십육 비트에서 십육 기가바이트, 팔 비트에서 팔 기가바이트, 사 비트에서 사 기가바이트입니다.

이 계산은 모든 파라미터를 같은 비트 수로 저장했다고 가정한 값입니다. 지피유에서 실제로 차지할 전체 공간은 다음 단계에서 더합니다. 또한 기가바이트는 십억 바이트이고 기비바이트는 이의 삼십 제곱 바이트입니다. 도구에 표시된 단위를 통일해야 계산값을 올바르게 비교할 수 있습니다. 먼저 단순한 식으로 후보 규모를 가늠한 뒤 실제 저장 방식과 실행 조건을 반영합니다.

제칠장. 사 비트 파일이 계산보다 커지는 이유

양자화된 모델은 압축한 숫자와 함께 그 숫자를 해석할 스케일 같은 부가 정보도 저장합니다. 일부 계층이 높은 정밀도로 남을 수도 있습니다. 어떤 계층을 바꾸는지는 변환 도구와 모델 구조, 설정에 따라 달라집니다.

가상의 팔십억 파라미터 모델에서 칠십억 개는 사 비트, 나머지 십억 개는 십육 비트로 남는다고 해 봅시다. 앞부분은 삼 점 오 기가바이트, 뒷부분은 이 기가바이트라서 합계는 오 점 오 기가바이트입니다. 여기에 양자화 메타데이터까지 추가됩니다. 모든 값을 사 비트로 놓고 구한 사 기가바이트와 차이가 생깁니다. 이 예시는 혼합 정밀도의 영향을 보여 주기 위해 만든 숫자이며 특정 모델의 측정값은 아닙니다.

제팔장. 답을 만드는 동안 늘어나는 캐시

언어 모델은 문장을 한 토큰씩 이어 만듭니다. 앞서 처리한 토큰의 키와 밸류를 저장해 두면 이전 계산의 일부를 재사용할 수 있습니다. 이 공간을 케이브이 캐시라고 부릅니다. 일반적인 전체 어텐션 구조에서는 저장한 토큰이 많아질수록 캐시도 커집니다.

입력 문서와 생성할 답변을 함께 생각해야 합니다. 문서가 사천 토큰이고 답변을 최대 천 토큰 만들 계획이라면 요청이 진행되면서 오천 토큰 수준까지 늘어날 수 있습니다. 동시에 처리하는 요청마다 캐시가 필요하므로 활성 요청 수도 중요합니다. 가입한 직원 수와 지금 계산 중인 요청 수는 구분합니다. 공통 앞부분을 공유하는 최적화가 있다면 실제 사용량은 단순 합계와 달라질 수 있습니다.

제구장. 캐시를 수식으로 읽기

일반적인 구조의 캐시 크기는 층 수, 토큰 수, 케이브이 헤드 수, 헤드 차원, 저장 자료형의 바이트 수를 곱해 추정합니다. 키와 밸류 두 종류라서 이에 이를 곱하고 동시 요청 수도 반영합니다. 여기서 사용하는 헤드 수는 케이브이 헤드 수입니다. 쿼리 헤드 수를 그대로 쓰면 계산이 어긋날 수 있습니다.

가상의 모델에 층 삼십이 개, 케이브이 헤드 여덟 개, 헤드 차원 백이십팔, 저장 자료형 이 바이트, 토큰 사천구십육 개를 넣으면 요청 하나의 캐시는 영 점 오 기비바이트입니다. 같은 요청 여덟 개라면 사 기비바이트가 됩니다. 그룹 쿼리 어텐션은 여러 쿼리 헤드가 키와 밸류를 공유하는 구조입니다. 하이브리드 구조나 슬라이딩 윈도우를 쓰는 모델은 해당 구조에 맞게 따로 계산합니다.

제십장. 모델 적재와 서비스 용량

운영 메모리는 가중치와 캐시 외에도 중간 계산, 실행 도구의 작업 공간, 메모리 할당 여유를 포함합니다. 모델을 불러온 직후의 사용량을 확인한 다음 긴 입력 하나, 동시 요청 여러 개 순서로 조건을 넓혀 봅니다.

예를 들어 사 비트 이론 가중치가 사 기가바이트인 후보는 이십사 기가바이트 지피유에서 검토해 볼 수 있습니다. 십육 기가바이트인 후보는 캐시와 나머지 공간을 더 신중히 계산해야 합니다. 총 천백억 파라미터인 후보는 같은 계산으로 오십오 기가바이트가 필요하므로 한 장에 전체를 적재하는 조건에서 제외됩니다. 몇 퍼센트를 더하는 여유 규칙은 초기 계획의 가정입니다. 최종 판단에는 실제 입력 길이와 동시 요청 조건의 측정값이 필요합니다.

제십일장. 양자화로 얻고 확인할 것

퀀타이제이션, 양자화는 숫자를 표현하는 정밀도를 낮춰 저장 공간이나 계산 부담을 줄이는 방법입니다. 가중치를 사 비트로 저장해도 계산 자료형이나 캐시 자료형은 별도 설정일 수 있습니다. 각각 무엇이 바뀌는지 확인해야 메모리 감소의 범위를 알 수 있습니다.

사 비트는 비교해 볼 만한 출발점입니다. 적절한 정밀도는 모델과 업무에 따라 달라집니다. 같은 모델을 높은 정밀도와 낮은 정밀도로 실행해 답변 내용, 형식 준수, 도구 인자, 긴 추론의 결과를 나눠 확인합니다. 평균 점수가 비슷해도 자주 쓰는 기능에서 실패가 늘면 선택이 달라집니다. 한국어의 숫자, 조사, 부정 표현도 평가에 포함합니다.

제십이장. 작은 파일과 빠른 응답의 관계

메모리에서 가중치를 읽는 일이 병목이라면 읽을 양을 줄이는 것이 도움이 될 수 있습니다. 하지만 낮은 정밀도의 값을 처리하는 커널이 하드웨어에 잘 맞아야 합니다. 변환 과정과 실행 도구의 지원 수준 때문에 기대한 만큼 빨라지지 않을 수도 있습니다.

속도는 처음 답이 나올 때까지의 시간, 답이 이어지는 속도, 서버 전체 처리량으로 나눠 봅니다. 혼자 짧게 물었을 때 빠른 설정이 동시 요청에서도 유리한지는 별도 문제입니다. 같은 문서 길이와 출력 길이, 같은 동시 요청 조건으로 측정합니다. 캐시가 준비된 요청과 처음 받는 요청도 기록에서 구분하면 결과를 해석하기 쉽습니다.

제십삼장. 저장 형식과 양자화 방법

지지유에프는 모델의 텐서와 관련 정보를 담는 파일 형식입니다. 여러 정밀도의 데이터를 담을 수 있습니다. 에이더블유큐와 지피티큐는 양자화 방법을 가리키며 배포 파일 이름에서도 자주 만납니다. 세 이름이 등장하더라도 같은 종류의 개념으로 뭉뚱그리면 도구 선택이 어려워집니다.

먼저 사용할 하드웨어와 운영 조건을 정하고 실행 도구가 지원하는 모델 구조, 양자화 방식, 버전을 확인합니다. 그 조합에 맞는 파일을 고릅니다. 특정 형식이 항상 개인용이고 다른 형식이 항상 운영용이라는 규칙은 두지 않습니다. 같은 형식도 실행 엔진과 설정에 따라 동시 처리 능력이 달라집니다. 내려받기 전 호환성 표를 확인하면 불필요한 변환을 줄일 수 있습니다.

제십사장. 라이선스에 적어 둘 네 질문

후보마다 라이선스 원문의 주소와 확인 날짜를 남깁니다. 사용 목적이 허용되는지, 규모나 용도에 조건이 붙는지, 수정한 모델을 다른 조직에 배포할 수 있는지, 출력물을 학습 등에 재사용할 때 제약이 있는지 확인합니다.

관련 조항과 우리 계획을 나란히 적으면 검토가 쉬워집니다. 예를 들어 사내 실험과 고객 대상 서비스, 자회사에 파일을 전달하는 방식과 서비스 접속만 제공하는 방식은 조건이 달라질 수 있습니다. 엔지니어가 문서에 적힌 조건을 추려 놓고 실제 계약과 서비스 계획에 적용할 판단은 담당자에게 확인합니다. 별도의 사용 정책이나 서비스 약관이 연결되어 있다면 함께 기록합니다.

제십오장. 같은 계열도 조건이 달라진다

이천이십육년 시월 팔일에 확인한 공식 자료에서 젬마 포는 아파치 이 점 영 라이선스로 안내됩니다. 이전 젬마 세대에 적용되는 별도 약관도 남아 있어 모델 버전을 함께 적어야 합니다. 엑사원 사 점 오는 연구와 교육 목적 중심의 엔씨 라이선스를 사용합니다. 상업적 운영을 계획한다면 별도 허가나 다른 후보를 검토해야 합니다.

솔라 오픈 투의 라이선스는 상업적 사용을 허용하면서 파생 인공지능 모델을 배포하거나 제공하는 경우 이름과 표시 조건을 둡니다. 해당 조건에 따라 이름을 솔라로 시작하고 빌트 위드 솔라 문구를 표시하도록 정합니다. 정확한 적용 범위는 원문과 제공 형태를 대조합니다. 이렇게 한 회사의 전체 모델을 한 줄로 판단하지 않고 정확한 모델과 문서를 연결해 둡니다.

제십육장. 다운로드 승인과 운영 준비

모델 저장소에는 접근 승인이 필요한 경우가 있습니다. 이를 게이티드 저장소라고 부릅니다. 허깅페이스의 접근 승인은 개별 사용자 단위이므로 팀원이 자신의 접근 권한을 갖췄는지 확인해야 합니다.

폐쇄된 네트워크에 모델을 들여올 계획이라면 파일을 받을 수 있는 계정, 라이선스 확인, 필요한 파일 목록과 버전, 파일의 해시를 미리 기록합니다. 실제 운영에 필요한 것은 가중치 외에도 토크나이저와 설정, 실행 환경일 수 있습니다. 복사한 파일만으로 서비스가 재현되는지도 확인합니다. 접근 승인은 사용 조건 검토와 별도 항목으로 두어야 일정과 권한 문제를 찾기 쉽습니다.

제십칠장. 외부 서비스와 자체 운영의 비용

외부 모델 에이피아이, 공개 모델을 호스팅하는 업체의 에이피아이, 자체 서버 운영을 비교해 봅시다. 앞의 두 방식은 업체의 과금 체계를 확인하고 자체 운영은 하드웨어와 운영 시간을 계산합니다. 데이터 처리 조건을 먼저 만족하는 선택지끼리 비용을 비교합니다.

토큰당 단가 외에도 실패 후 재시도, 긴 답변, 검색과 도구 호출, 사람이 검토하는 시간을 포함합니다. 저렴한 후보가 한 번에 끝낼 일을 여러 번 시도한다면 업무 한 건의 총액이 커질 수 있습니다. 반대로 단순한 분류를 작은 모델이 안정적으로 처리한다면 비싼 모델의 호출을 줄일 수 있습니다. 같은 업무를 같은 품질 기준으로 완료하는 비용을 비교합니다.

제십팔장. 입력과 출력 비용을 따로 계산하기

다음은 실제 서비스의 요금이 아닌 계산 연습입니다. 문서 백 건을 처리하고 한 건당 입력 육천 토큰, 출력 오백 토큰을 사용한다고 가정합니다. 백만 토큰당 입력 단가는 영 점 팔 달러, 출력 단가는 이 점 사 달러로 놓겠습니다.

총 입력은 육십만 토큰이라 영 점 사팔 달러입니다. 총 출력은 오만 토큰이라 영 점 일이 달러입니다. 두 값을 더하면 영 점 육 달러입니다. 여기에 실제 견적에서는 캐시 요금, 별도로 과금되는 추론 토큰과 도구, 재시도 등을 해당 업체의 기준에 맞춰 더합니다. 입력과 출력을 한 숫자로 합친 뒤 하나의 단가를 곱하면 과금 구조를 놓칠 수 있습니다.

제십구장. 자체 운영과 가동률

자체 서버의 월 비용에는 임대료나 장비 감가상각, 전력, 운영 인력, 감시와 예비 용량을 포함합니다. 설명용으로 월 총비용이 육백 달러이고 실제 처리량이 육천만 토큰이라면 백만 토큰당 십 달러입니다. 같은 비용으로 육백만 토큰만 처리하면 백 달러가 됩니다.

이 계산은 사용량 변화의 영향을 보여 줍니다. 입력과 출력 비율, 문서 길이, 품질 조건이 같은 상황에서 비교해야 의미가 있습니다. 지피유 사용률 그래프의 숫자와 업무 처리량도 구분해야 합니다. 평소에는 한가하고 특정 시간에만 요청이 몰린다면 평균 처리량뿐 아니라 대기 시간과 최대 부하를 감당할 예비 용량을 함께 계획합니다.

제이십장. 한국어 토큰과 견적

같은 뜻의 한국어와 영어가 몇 토큰이 되는지는 토크나이저와 문장에 따라 달라집니다. 한국어 비용에 항상 두 배를 곱하는 고정 규칙을 두기보다 실제 문서를 각 후보의 토크나이저로 세어 봅니다.

문서 본문에 시스템 지시, 검색한 근거, 대화 기록, 출력 여유를 더한 길이가 실제 입력 계획입니다. 컨텍스트 한도가 팔천 토큰이면 어느 언어든 그 토크나이저로 센 팔천 토큰이 기준입니다. 그 안에 담기는 글자 수가 달라집니다. 같은 백 건을 처리할 때 입력과 출력 토큰이 얼마나 나오는지 기록한 다음 단가를 곱하면 업무에 가까운 견적이 됩니다.

제이십일장. 후보를 줄이는 순서

먼저 데이터가 이동할 수 있는 범위와 수행할 업무를 정합니다. 다음으로 모델의 입력 종류와 사용 조건을 확인하고 가중치와 캐시, 실행 환경을 검토합니다. 이 단계는 큰 파일을 모두 내려받기 전에도 상당 부분 진행할 수 있습니다.

남은 후보를 같은 업무 평가로 비교합니다. 품질, 응답 시간, 동시 처리량, 비용을 함께 기록합니다. 후보가 탈락한 이유도 남깁니다. 사용 조건 때문인지, 한 장에 전체를 올릴 수 없기 때문인지, 한국어 항목 추출에서 오류가 많기 때문인지 적어 두면 요구사항이 바뀌었을 때 다시 검토할 위치를 알 수 있습니다. 애매한 라이선스 항목은 확인 대기로 표시합니다.

제이십이장. 채점기에도 시험이 필요하다

예를 들어 출력에서 승인 여부를 검사하면서 승인이라는 단어가 있으면 정답으로 처리했다고 해 봅시다. 승인하지 않는다는 답도 승인이라는 글자를 포함합니다. 이런 규칙으로 얻은 점수는 업무 정답률과 다를 수 있습니다.

정답, 반대 답, 빈 답, 관계없는 답을 채점기에 넣어 판정이 기대와 맞는지 확인합니다. 형식 검사와 내용 검사를 분리하는 것도 도움이 됩니다. 제이슨으로 읽을 수 있다는 사실과 그 안의 날짜나 금액이 맞다는 사실은 각각 확인합니다. 여러 후보가 모두 높은 점수를 얻으면 문제가 쉬운지, 자료가 편중됐는지, 채점 조건이 느슨한지 살펴봅니다. 높은 점수 자체만으로 원인을 단정하지 않습니다.

제이십삼장. 모델을 바꾸기 전에 실패 경로 읽기

사내 문서 답변이 틀렸다면 검색된 문서부터 살펴봅니다. 필요한 조항이 검색 결과에 들어 있는지, 프롬프트가 그 내용을 제대로 전달했는지, 입력이 잘렸는지 확인합니다. 이어 출력 형식과 실제 답의 의미를 보고 마지막으로 채점이 맞는지 점검합니다.

이 과정에서 모델이 충분한 근거를 받아도 반복해서 틀리는지 확인할 수 있습니다. 검색 문제라면 검색을 고치고 형식 문제라면 형식 제약이나 검증을 조정합니다. 모델을 교체할 때는 같은 평가 묶음으로 다시 비교합니다. 양자화 설정이나 대화 형식이 함께 바뀌었다면 그 변화도 기록해 결과의 원인을 추적합니다.

제이십사장. 선정 보고서에 남길 것

선정 기록에는 업무와 데이터 경계, 정확한 모델 버전, 사용 조건의 근거, 메모리 계산의 가정, 측정한 품질과 속도, 예상 비용을 적습니다. 후보별 탈락 이유와 미확인 항목도 남깁니다. 직접 측정한 결과와 계산으로 추정한 값은 표시를 구분합니다.

재검토 조건도 구체적으로 정합니다. 동시 요청이 계획을 넘거나 문서 길이가 늘었을 때, 업무 평가의 실패가 늘었을 때, 모델이나 라이선스 버전을 바꿀 때 다시 살펴봅니다. 메모리는 무엇을 얼마나 저장하는지로 계산하고 비용은 같은 업무를 완료하는 조건으로 비교합니다. 이 기록이 있으면 다음 모델을 검토할 때도 판단의 출발점을 이어 갈 수 있습니다.
