사내 문서에 답하는 모델을 고르려면 질문이 구체적이어야 한다. 문서를 어디로 보낼 수 있는지, 어떤 용도로 쓸지, 동시에 몇 건을 처리할지, 어느 정도의 오류를 허용할지에 따라 후보가 달라진다. 이 조건을 정해 놓으면 모델의 크기와 성능을 비교할 기준도 생긴다.

모델의 공개 방식부터 메모리, 양자화, 라이선스, 비용, 업무 평가까지 정리했다. 음성은 같은 개념을 말로 풀어 설명한다. 본문에는 계산표와 직접 만든 Python 예제를 더했다. 모델·라이선스의 공식 자료 확인일은 **2026년 10월 8일**이며, 비용 예시는 계산 방법을 설명하려고 만든 가상 값이다.

## 1. 가중치 공개와 실행 장소

Open weights(공개 가중치)는 학습된 파라미터를 내려받을 수 있다는 뜻이다. 사용·수정·재배포 범위는 해당 모델의 License(라이선스)에서 확인한다. 가중치를 받을 수 있는지와 원하는 사업에 사용할 수 있는지는 각각 살펴야 한다.

Open source AI(오픈소스 AI)는 더 넓은 조건을 다룬다. OSI의 정의에는 사용·연구·수정·공유의 자유와 함께 파라미터, 코드, 학습 데이터에 관한 충분한 정보가 포함된다. 이를 모든 원시 학습 데이터의 공개 여부 하나로 설명하면 정의를 지나치게 단순화한다. [OSI Open Source AI Definition 1.0](https://opensource.org/ai/open-source-ai-definition)

실행 장소는 공개 방식과 별도로 적는다. 공개 모델을 회사 서버에 올릴 수도 있고 외부 업체가 호스팅한 API로 이용할 수도 있다. 외부 추론 서비스에 요청하면 그 서비스로 입력이 전송된다. 자체 서버에서도 검색·로그·오류 추적·모니터링 경로를 함께 확인해야 전체 데이터 경계를 설명할 수 있다.

| 구성 | 모델을 실행하는 곳 | 먼저 확인할 내용 |
|---|---|---|
| 제공사 모델 API | 제공사의 인프라 | 데이터 처리 조건, 모델 버전, 요금 |
| 공개 모델 호스팅 API | 호스팅 업체의 인프라 | 모델 사용 조건과 서비스 계약, 실행 지역 |
| 자체 운영 | 직접 관리하는 서버 | 라이선스, 메모리, 접근 통제, 운영 부담 |

비용 비교는 허용된 데이터 처리 조건 안에서 한다. 외부 전송을 허용하는 계약이 있는지, 특정 등급의 문서만 제한되는지부터 정하면 실제로 비교할 선택지가 좁아진다.

## 2. 모델 계열을 후보 목록으로 바꾸기

Qwen, Llama, Gemma, Mistral, DeepSeek 같은 계열명은 자료를 찾는 출발점이다. 한국어 업무라면 Solar와 EXAONE 같은 계열도 살펴볼 수 있다. 선정표에는 정확한 저장소 ID와 Revision(버전 식별자), 확인 날짜를 넣는다. 같은 계열 안에서도 크기, 입력 종류, 대화 형식, 사용 조건이 달라질 수 있다.

Base model(기반 모델)과 Instruction-tuned model(지시 학습 모델)도 구분한다. 전자는 다음 내용을 예측하도록 학습한 바탕 모델이고, 후자는 지시 수행에 맞춘 추가 학습을 거친 모델이다. 챗봇 후보를 고를 때는 대화용 버전과 Chat template(채팅 형식)을 함께 확인한다. 계열이 같더라도 새 버전에서 입력 처리와 권장 설정이 그대로 유지된다고 가정하지 않는다.

모델 카드에는 지원 입력, 구조, 크기, 평가 조건, 사용법과 라이선스 링크가 모인다. 다운로드 수와 커뮤니티 자료는 문제 해결에 참고가 된다. 업무 정확도는 별도로 측정한다. 규모가 작은 모델도 후보에 넣되, 필요한 품질을 충족하는지는 실제 업무로 확인한다.

## 3. MoE의 두 숫자 읽기

Mixture of Experts(MoE, 전문가 혼합)는 여러 전문가 모듈 가운데 일부를 선택해 계산하는 구조다. Total parameters(총 파라미터)는 전체 모델의 크기이고 Active parameters(활성 파라미터)는 토큰 처리에 참여하는 규모다.

Qwen3.5-397B-A17B의 공식 모델 카드는 언어 모델의 총 파라미터를 397B, 활성 파라미터를 17B로 안내한다. 여기서 B는 십억 단위다. 가중치를 모두 GPU에 적재한다면 전체 가중치를 보관할 공간을 계산해야 한다. 활성 17B만 넣어 메모리를 구하면 필요한 용량을 크게 낮춰 잡게 된다. [Qwen3.5-397B-A17B 모델 카드](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)

활성 규모는 계산량을 가늠하는 단서다. 실제 속도에는 메모리 대역폭, 전문가 선택, 장치 사이 통신, Batch(배치) 크기와 실행 구현도 영향을 준다. CPU나 다른 장치에 일부를 두는 Offloading(오프로딩)을 쓰면 GPU 메모리는 줄일 수 있지만 데이터 이동에 드는 시간도 확인해야 한다. GPU 한 장이라는 조건만으로 모든 MoE를 제외하기보다 총 크기와 적재 방식을 먼저 본다.

## 4. 가중치 메모리의 첫 어림셈

모든 파라미터를 같은 정밀도로 저장한다고 가정하면 가중치 크기는 다음과 같다.

`가중치 바이트 = 파라미터 수 × 비트 수 ÷ 8`

| 파라미터 수 | 16bit | 8bit | 4bit |
|---|---:|---:|---:|
| 8B | 16GB | 8GB | 4GB |
| 32B | 64GB | 32GB | 16GB |
| 110B | 220GB | 110GB | 55GB |

표는 **가중치만의 이론값**이다. Quantization(양자화)에 필요한 부가 정보, 높은 정밀도로 남긴 계층, KV cache(키·값 캐시), 실행 중 작업 공간은 포함하지 않았다. 24GB GPU라면 8B는 여유를 계산해 볼 후보이고, 32B는 나머지 공간을 더 꼼꼼히 확인할 후보다. 110B는 4bit 이론 가중치만 55GB이므로 한 장에 전체를 적재하는 조건에서 제외된다.

단위도 맞춘다. GB는 10억 바이트, GiB는 2의 30제곱 바이트다. 예를 들어 16GB는 약 14.9GiB다. GPU 도구가 표시하는 값과 비교할 때 같은 단위를 써야 한다.

## 5. 실제 가중치가 어림셈보다 커지는 이유

4bit 모델에는 압축한 값뿐 아니라 그 값을 해석하는 Scale(스케일) 등의 정보가 들어간다. 어떤 계층을 양자화하고 어떤 계층을 높은 정밀도로 남기는지도 도구와 설정에 따라 달라진다. Transformers의 bitsandbytes 통합은 선형 계층을 양자화하는 경로를 제공한다. Embedding(임베딩)과 출력 계층까지 모든 파라미터가 똑같이 바뀐다고 가정하면 실제 크기와 차이가 생긴다. [bitsandbytes 공식 문서](https://huggingface.co/docs/transformers/main/quantization/bitsandbytes)

설명용으로 8B 모델의 7B를 4bit, 나머지 1B를 16bit로 저장한다고 해 보자. 앞부분은 3.5GB, 뒷부분은 2GB라서 합계가 5.5GB다. 여기에 양자화 메타데이터가 더해진다. 같은 8B를 전부 4bit로 놓은 4GB와 차이가 난다. 혼합 정밀도 계산 예시로 만든 숫자이며 특정 모델의 실측값과 구분한다.

확인 순서는 모델 구조와 변환 설정, 배포 파일, 적재 후 메모리 사용량으로 이어진다. Embedding과 출력 계층이 가중치를 공유하는 구조인지도 계산에 영향을 준다. 모델 크기만으로 오차를 고정 비율로 정하기는 어렵다.

## 6. KV 캐시는 요청과 함께 자란다

Autoregressive generation(자기회귀 생성)은 앞의 토큰을 바탕으로 다음 토큰을 만든다. 앞서 계산한 Key(키)와 Value(값)를 저장하면 이전 계산의 일부를 재사용할 수 있다. 일반적인 Full attention(전체 어텐션) 구조에서는 토큰이 쌓일수록 캐시도 늘어난다. [Transformers의 캐시 설명](https://huggingface.co/docs/transformers/main/cache_explanation)

단순한 구조에서 캐시 바이트를 추정하는 식은 다음과 같다.

`2 × 층 수 × 동시 요청 수 × 저장 토큰 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트`

앞의 2는 키와 값 두 종류를 뜻한다. 저장 토큰 수에는 입력과 이미 생성한 출력이 들어간다. 용량 계획에서는 예상 최대 출력도 고려한다. Grouped-query attention(GQA, 그룹 쿼리 어텐션)은 여러 쿼리 헤드가 키·값을 공유하므로 계산에 넣는 헤드 수를 확인해야 한다. [GQA 논문](https://arxiv.org/abs/2305.13245)

가상의 구조를 층 32개, KV 헤드 8개, 헤드 차원 128, 자료형 2바이트, 요청당 4,096토큰으로 놓으면 캐시는 요청 하나당 0.5GiB다. 같은 요청이 8개면 4GiB가 된다. 직원 100명이 등록되어 있어도 동시에 처리 중인 요청이 3개라면 필요한 계산의 기준은 활성 요청이다.

이 식은 단순한 전체 어텐션 캐시의 근사다. Sliding window(슬라이딩 윈도우), 하이브리드 구조, 공유 Prefix cache(접두부 캐시), 캐시 양자화, 블록 할당을 사용하면 실제 저장 방식에 맞춰 계산해야 한다. 최신 모델의 설정 파일을 읽을 때도 구조가 이 가정에 맞는지 먼저 확인한다.

## 7. 서비스 용량에는 실행 공간도 필요하다

운영 메모리는 가중치, 캐시, 중간 계산, Runtime(실행 환경)의 작업 공간과 여유분을 합쳐 본다. 가중치 적재에 성공했더라도 긴 입력이나 동시 요청에서 메모리 부족이 생길 수 있다.

확인은 모델을 불러온 직후, 긴 입력 한 건, 여러 요청이 겹치는 조건으로 나눠 진행한다. Prefill(입력 처리)과 Decode(토큰 생성)의 메모리·시간 특성도 다를 수 있다. 여유를 20~40% 더하는 규칙은 계획 단계에서 쓸 수 있는 가정이다. 정확한 여유는 모델과 엔진, 입력 분포를 측정해 정한다.

선정표에는 `입력 최대 4,096토큰, 출력 최대 512토큰, 동시 요청 8건`처럼 조건을 남긴다. 아직 실행하지 않았다면 추정값이라고 표시한다. 이 글의 메모리 숫자는 수식 검산이며 실제 GPU 수용량을 측정한 결과는 아니다.

## 8. 양자화의 품질과 속도를 따로 보기

양자화는 낮은 정밀도의 수치 표현으로 저장·계산 부담을 줄이는 방법이다. Weight precision(가중치 정밀도), Compute dtype(계산 자료형), KV cache dtype(캐시 자료형)은 각각 확인한다. 가중치가 4bit라도 캐시는 16bit일 수 있다.

4bit는 비교를 시작할 후보 설정으로 둘 수 있다. 적정 비트 수와 품질 저하의 폭은 모델, 변환 방법, 업무에 따라 달라진다. 같은 모델의 높은 정밀도 버전과 비교해 요약 내용, 항목 추출, JSON 형식, 도구 인자, 다단계 추론을 나눠 본다. 특정 기능에서 오류가 늘었다면 그 기능의 사용 비중도 판단에 반영한다.

가중치를 읽는 메모리 대역폭이 병목일 때는 작은 표현이 속도에 도움이 될 수 있다. 실제 이득은 하드웨어와 Kernel(연산 구현)의 지원에 달려 있다. 첫 응답 지연, 생성 속도, 서버 전체 처리량을 같은 입력 길이와 동시 요청 조건에서 비교한다. 양자화 파일 크기만으로 응답 속도를 확정하지 않는다.

## 9. 실행 도구와 파일의 조합

GGUF는 텐서와 메타데이터를 담는 파일 형식이다. 여러 정밀도의 텐서를 담을 수 있다. AWQ와 GPTQ는 양자화 방법을 가리키며 모델 배포 이름에도 사용된다. 형식과 알고리즘의 역할을 구분하면 다운로드 목록을 읽기 쉬워진다. [GGUF 형식 명세](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)

순서는 `하드웨어·동시 처리 조건 → 실행 엔진 → 지원 모델 구조·양자화 구현 → 배포 파일`로 잡는다. llama.cpp, Ollama, vLLM 등에서 어떤 조합을 지원하는지 버전별로 확인한다. vLLM의 공식 지원표도 양자화 구현과 하드웨어를 나눠 표시한다. AWQ를 특정 제조사 전용이라고 고정하거나 GGUF를 개인용으로 한정하면 실제 지원 범위를 놓칠 수 있다. [vLLM 양자화·하드웨어 지원표](https://docs.vllm.ai/en/latest/features/quantization/)

혼자 시험한 환경에서 여러 사람의 서비스로 옮길 때는 동시에 들어오는 요청 수, 대기열, 메모리 제한, 실패 처리도 다시 확인한다. 사무실 인원수와 지속적인 동시 요청 수를 구분해서 부하 조건을 정한다.

## 10. 라이선스는 정확한 버전에서 확인하기

라이선스 태그는 원문을 찾는 단서다. 원문에서 사용 목적, 규모·용도 제한, 수정·배포, 출력물의 재사용 조건을 찾고 별도 사용 정책이 연결되어 있는지도 확인한다. 2026년 10월 8일에 확인한 사례를 놓으면 차이가 보인다.

| 대상 | 공식 자료에서 확인한 조건 | 기록할 판단 |
|---|---|---|

Qwen의 해당 저장소에는 [Apache 2.0 라이선스 원문](https://huggingface.co/Qwen/Qwen3.5-397B-A17B/blob/main/LICENSE)이 있다. Google은 [Gemma 4 모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4)에서 Apache 2.0을 안내하고, [기존 Gemma 약관](https://ai.google.dev/gemma/terms)은 적용 모델 목록을 따로 둔다. 계열 전체의 과거·현재 조건을 한 문장으로 합치면 적용 버전을 놓친다.

[EXAONE 4.5 라이선스](https://github.com/LG-AI-EXAONE/EXAONE-4.5/blob/main/LICENSE)는 연구·교육 목적의 허용 범위를 규정한다. 상업적 운영을 계획한다면 별도 허가 가능성이나 다른 후보를 검토한다. [Solar 라이선스 4(e)](https://huggingface.co/upstage/Solar-Open2-250B/blob/main/LICENSE)는 파생 AI 모델을 배포하거나 제공할 때 모델 이름을 `Solar`로 시작하고 관련 웹사이트·화면·문서에 `Built with Solar`를 표시하는 등의 조건을 둔다.

기술 검토에서는 해당 조항과 우리 제공 방식을 나란히 적는다. 사내 실험, 고객 대상 서비스, 자회사로 파일 전달, 서비스 접속 제공은 검토할 형태가 다르다. 실제 적용 판단이 필요한 조항은 계약·법무 담당자에게 확인할 항목으로 남긴다.

## 11. 접근 승인과 재현에 필요한 파일

Gated repository(접근 승인 저장소)는 모델을 받기 전에 사용자 정보 제출이나 승인이 필요할 수 있다. Hugging Face의 접근 승인은 개별 사용자에게 부여된다. 팀과 운영 계정이 필요한 권한을 갖췄는지 확인해야 한다. [Hugging Face 접근 승인 문서](https://huggingface.co/docs/hub/models-gated)

폐쇄망으로 들여올 계획이라면 가중치와 토크나이저, 설정 파일, 필요한 실행 환경을 함께 정리한다. 정확한 버전과 파일 Hash(해시)를 기록하면 같은 자료를 사용했는지 확인하기 쉽다. 다운로드 가능 여부, 사용 조건, 운영 재현 여부를 각각 체크한다.

자체 운영은 모델 버전을 직접 고정할 수 있다는 장점이 있다. 재현성을 유지하려면 가중치뿐 아니라 토크나이저·엔진·연산 설정도 관리해야 한다. API를 검토할 때는 고정 버전 제공 여부와 종료 정책, 이전 계획을 함께 살펴본다.

## 12. API는 입력과 출력을 나눠 계산하기

API 비용은 실제 과금 단위별로 계산한다. 다음 값은 **실제 요금표가 아닌 가상 단가**다. 문서 100건, 건당 입력 6,000토큰과 출력 500토큰, 백만 토큰당 입력 $0.8·출력 $2.4라고 가정한다.

입력은 총 600,000토큰이므로 $0.48, 출력은 50,000토큰이므로 $0.12다. 합계는 $0.60이다. 실제 견적에서는 캐시된 입력, 별도로 과금되는 추론 토큰, 도구·검색, 재시도 등을 업체의 과금 기준에 맞춰 반영한다.

비교 단위는 같은 업무 100건을 같은 품질 기준으로 완료한 총액으로 두면 편하다. 낮은 단가의 모델에서 재시도나 사람의 검토가 늘면 업무당 비용이 커질 수 있다. 반대로 간단한 분류를 작은 모델이 안정적으로 처리하면 더 큰 모델의 호출 수를 줄일 수 있다.

## 13. 자체 운영은 가동률과 예비 용량까지

자체 운영 비용에는 장비 감가상각 또는 임대료, 전력, 운영 인력, 모니터링, 장애 대비 용량을 넣는다. 월 고정비를 실제 처리량으로 나누면 사용량 변화가 단가에 미치는 영향을 확인할 수 있다.

설명용으로 월 총비용을 $600으로 놓자. 월 처리량이 60,000,000토큰이면 백만 토큰당 $10이고, 6,000,000토큰이면 $100이다. 이 계산은 동일한 입력·출력 구성과 품질 조건에서 사용량이 줄어드는 상황을 가정한다. GPU 이용률 그래프의 수치와 실제 업무 처리량도 구분해야 한다.

손익분기는 장비·모델·문서 길이·요청 분포·운영 비용에 따라 달라진다. 특정 가동률 하나를 모든 서비스의 기준으로 쓰기는 어렵다. 평균 사용량 외에 Peak load(최대 부하)와 응답 시간 목표를 함께 본다. 여러 업무를 한 서버에 모을 때도 한 업무의 급증이 다른 업무를 밀어내는지 확인한다.

## 14. 한국어는 실제 토크나이저로 세기

Tokenizer(토크나이저)는 문자열을 모델이 다루는 토큰으로 나눈다. 같은 의미의 한국어와 영어가 몇 토큰이 되는지는 문장과 토크나이저에 따라 달라진다. 견적에 일정한 언어 배수를 곱하기보다 실제 업무 문서를 후보별로 세어 본다.

Context window(컨텍스트 한도)가 8,000토큰이라면 해당 토크나이저 기준으로 8,000토큰이다. 그 안에 들어가는 글자 수가 언어와 문서에 따라 달라진다. 시스템 지시, 검색된 근거, 대화 기록, 답변에 남길 공간까지 포함해 길이를 계산한다.

한국어 평가는 요약, 추출, 분류, 근거 답변, 형식 출력처럼 업무별로 나눈다. 숫자·날짜·부정 표현·사내 용어·근거가 부족한 질문을 포함하고, 이름을 가린 후보 답변을 비교하면 선입견을 줄이는 데 도움이 된다. 20건 정도는 실패 유형을 찾는 출발점으로 쓸 수 있다. 운영 품질을 확정하려면 대표성 있는 더 넓은 평가와 지속적인 관찰이 필요하다.

## 15. 계산만 확인하는 작은 예제

아래 코드는 이 글의 가정과 단위만 계산한다. 모델을 내려받거나 API를 호출하지 않는다. 실제 모델의 구조 분석과 GPU 성능 측정은 포함하지 않는다.

```python
def weight_gb(params_b, bits):
    return params_b * bits / 8


def kv_gib(layers, requests, tokens, kv_heads, head_dim, dtype_bytes):
    return (2 * layers * requests * tokens * kv_heads
            * head_dim * dtype_bytes) / 2**30


def api_cost(input_tokens, output_tokens, input_price, output_price):
    return (input_tokens * input_price + output_tokens * output_price) / 1_000_000


print(f"8B / 4bit 가중치: {weight_gb(8, 4):.1f} GB")
print(f"혼합 정밀도 가중치: {weight_gb(7, 4) + weight_gb(1, 16):.1f} GB")
print(f"8개 요청 KV 캐시: {kv_gib(32, 8, 4096, 8, 128, 2):.1f} GiB")
print(f"가상 단가의 100건 비용: ${api_cost(600_000, 50_000, 0.8, 2.4):.2f}")
```

```text
8B / 4bit 가중치: 4.0 GB
혼합 정밀도 가중치: 5.5 GB
8개 요청 KV 캐시: 4.0 GiB
가상 단가의 100건 비용: $0.60
```

입력은 파라미터 수·정밀도, 캐시 구조·요청 조건, 토큰 수·가상 단가다. 함수는 각각 GB, GiB, 달러를 반환한다. 예제는 Python 표준 기능만 사용하며, 표시한 출력과 단위 계산을 실행해 확인했다. 실제 모델 다운로드·GPU 추론·성능 평가는 수행하지 않았다.

## 16. 남은 후보를 업무 평가로 고르기

후보를 좁히는 순서는 데이터 경계와 업무 요구사항, 입력 종류, 사용 조건, 메모리·실행 환경, 업무 평가로 이어진다. 파일을 받기 전에 확인할 수 있는 항목부터 검토하면 무거운 실험을 줄일 수 있다. 불명확한 라이선스 항목은 확인 대기로 표시한다.

남은 후보에는 같은 질문과 근거, 생성 조건을 적용한다. 품질과 함께 첫 응답 시간, 전체 처리 시간, 동시 처리량, 업무당 비용을 기록한다. 최종 운영 구성에서 프롬프트나 양자화 설정을 조정했다면 그 구성을 다시 평가한다.

채점기도 시험해야 한다. `승인`이 포함되면 정답으로 처리하는 규칙은 `승인하지 않는다`까지 통과시킨다. 정답·반대 답·빈 답·무관한 답을 넣어 판정부터 확인한다. JSON 파싱 성공과 필드 값의 정확성은 별도 검사로 둔다. 높은 점수가 나왔다면 문제 난도, 표본 구성, 채점 조건을 살펴보고 원인을 판단한다.

오답은 `검색된 근거 → 실제 모델 입력 → 생성 결과 → 채점 결과` 순서로 읽는다. 근거 누락, 입력 잘림, 불분명한 지시, 형식 오류, 내용 오류는 수정할 위치가 다르다. 모델이 충분한 근거와 적절한 입력을 받아도 반복해서 실패하는지 확인하면 교체 근거를 더 구체적으로 만들 수 있다.

## 17. 선정 결과와 재검토 조건 남기기

선정 보고서에는 업무·데이터 경계, 정확한 모델 버전, 라이선스 근거와 확인 날짜, 메모리 가정, 측정한 품질·속도, 비용을 적는다. 후보를 제외한 이유와 미확인 항목도 남긴다. 측정값과 추정값을 구분해 두면 나중에 조건이 바뀌었을 때 다시 계산할 수 있다.

재검토 조건은 동시 요청 증가, 문서 길이 변화, 업무 평가의 실패 증가, 모델·라이선스 버전 변경처럼 확인 가능한 사건으로 정한다. 기록한 판단 근거는 다음 선택에서도 이어서 참고할 수 있다.
