제일장. 모델 주변의 네 역할

같은 모델을 사용해도 어떤 정보를 넣고, 답을 어떻게 검사하고, 몇 번 다시 시도하는지에 따라 결과가 달라집니다. 오늘은 모델 주변의 일을 프롬프트, 컨텍스트, 하네스, 루프로 나누어 살펴봅니다.

프롬프트에는 목표와 작성 조건을 적습니다. 컨텍스트에는 그 지시와 함께 질문, 문서, 대화 기록을 담습니다. 하네스는 모델 호출과 도구 실행, 검사와 기록을 연결하는 프로그램입니다. 루프는 받은 결과를 보고 계속할지 멈출지 정합니다.

실제로는 이 역할들이 겹칩니다. 넓은 뜻의 하네스 안에 컨텍스트 관리와 루프가 들어갑니다. 네 가지로 나누는 목적은 답변에 문제가 생겼을 때 고칠 위치를 찾는 것입니다. 문서가 빠졌는지, 검사 기준이 잘못됐는지, 같은 실패를 반복하는지부터 구분합니다.

제이장. 프롬프트에 적을 것

프롬프트는 작업의 목표, 사용할 근거, 지켜야 할 조건, 결과의 모양을 전달합니다. 예를 들어 장비 대여 안내를 만든다면 대여 규정만 근거로 삼고, 기간과 승인 조건을 함께 적으며, 자료에 없는 내용은 확인이 필요하다고 답하게 할 수 있습니다. 여기서 장비 대여는 설명을 위해 만든 예시입니다.

자료 자체가 빠진 상황에서는 지시문의 표현만 바꾸어도 답할 근거가 생기지 않습니다. 답변이 맞는지 검사할 방법도 별도로 필요합니다. 작업을 여러 번 시도한다면 종료 조건까지 정해야 합니다.

그래서 답변이 나쁠 때는 지시의 명확성, 입력 자료의 충분성, 검사 방법, 반복 구조를 차례로 살핍니다. 모델이 해야 할 일을 설명하는 부분과 프로그램이 직접 보장하는 부분을 구분하면 수정 범위를 좁힐 수 있습니다.

제삼장. 컨텍스트 윈도우와 두 종류의 예산

컨텍스트 윈도우는 모델이 한 번에 다루는 토큰 범위입니다. 토큰은 모델이 텍스트를 나누어 읽는 단위입니다. 같은 글자 수라도 언어와 토크나이저에 따라 토큰 수가 달라집니다.

입력에는 시스템 지침, 도구 설명, 문서, 대화 기록, 현재 질문이 들어갈 수 있습니다. 답변 생성에 필요한 공간도 함께 고려합니다. 구성 요소별 토큰 수를 보면 어느 부분을 줄일지 판단하기 쉽습니다.

입력이 한도 안에 들어가는지와 필요한 정보를 잘 활용하는지는 따로 확인합니다. 긴 문서 안에 관련 없는 내용이 많으면 중요한 조건을 놓칠 수 있습니다. 어텐션 예산은 이런 정보 활용의 한계를 설명하는 표현입니다. 모델이 공개하는 별도의 잔량 계기처럼 해석하지 않고, 실제 질문에 대한 답변 품질로 확인합니다.

제사장. 챗 템플릿을 거치는 입력

실습에서 메시지스는 역할과 내용을 가진 항목들의 목록입니다. 시스템 역할에는 지침을, 유저 역할에는 질문을 넣고, 어시스턴트 역할에는 이전 답변을 넣습니다.

챗 템플릿은 이 목록에 모델별 역할 구분자와 발화 시작·종료 표시를 붙입니다. 어플라이 챗 템플릿 함수가 그 변환을 수행합니다. 토크나이즈를 폴스로 두면 읽을 수 있는 문자열을 확인하고, 트루로 두면 토큰 아이디를 얻습니다. 여기서 폴스와 트루는 설정값입니다.

애드 제너레이션 프롬프트는 지원하는 템플릿에서 다음 어시스턴트 응답의 시작 표시를 붙입니다. 구체적인 표시는 모델마다 다릅니다. 문자열로 변환한 뒤 다시 토큰화할 때에는 특수 토큰이 중복해서 붙는지도 확인합니다. 실제로 모델에 전달되는 입력을 보는 것이 이 단계의 목적입니다.

제오장. 로컬 실행과 엔드포인트

제공된 구현 노트북의 기본 백엔드는 로컬입니다. 큐웬 이 점 오 칠 비 인스트럭트 모델을 사 비트로 불러와 현재 실행 환경의 지피유에서 답을 생성합니다. 모델 가중치를 줄여 올리는 설정과 생성할 답변 길이의 설정은 서로 다른 역할입니다.

엔드포인트를 선택하면 별도로 준비한 추론 서버에 메시지를 보냅니다. 주소와 모델명, 인증값은 그 서버에 맞춰 설정합니다. 챗 함수는 두 경로에서 받아온 결과를 답변 문자열로 돌려줍니다.

다만 일부 실습 셀은 로컬 모델 객체와 쿠다를 직접 사용합니다. 백엔드 설정 하나를 바꾼 뒤 전체 노트북이 같은 방식으로 실행된다고 가정하면 이 부분을 놓칩니다. 이번 음성은 코드를 읽어 설명한 자료이며, 모델을 새로 내려받거나 지피유 추론을 다시 실행한 결과는 포함하지 않습니다.

제육장. 토큰 표에서 알 수 있는 것

실습은 문서를 조항별로 나누고 시스템 지침, 도구 설명, 문서, 대화 기록, 질문의 토큰 수를 각각 계산합니다. 이 표는 구성 요소의 크기를 비교하는 데 유용합니다.

문자열을 따로 세어 더한 값과 실제 메시지 전체의 토큰 수는 차이가 날 수 있습니다. 역할 구분자, 문서 사이의 줄바꿈, 생성 시작 표시 같은 요소도 입력에 들어가기 때문입니다. 생성할 답변 길이까지 별도로 잡아 둡니다.

표에 등장하는 도구 설명과 이전 대화는 뒤의 간단한 래그 답변 함수에는 전달되지 않습니다. 표가 가정한 구성과 함수가 실제로 보내는 구성을 나누어 읽어야 합니다. 계산에 사용한 값, 모델에 전달한 값, 모델이 반환한 값을 각각 짚어 보면 코드 흐름이 선명해집니다.

제칠장. 문서를 고르는 일

탑 케이는 보통 순위를 매긴 후보 중 몇 개를 가져올지 정하는 값입니다. 제공된 간단한 예제에서는 청크 목록의 앞에서 케이 개를 자릅니다. 이 함수 안에는 질문과의 관련도를 계산하는 검색이나 리랭킹이 들어 있지 않습니다.

따라서 케이를 줄이면 원래 순서의 뒤쪽에 있던 정답 조항이 빠질 수 있습니다. 토큰 수가 줄었는지와 질문에 필요한 근거가 남았는지를 함께 살펴야 합니다.

선별은 답에 필요한 일부 문서를 고를 때 유용합니다. 전체 문서의 모든 항목을 빠짐없이 정리하는 작업이라면 일부만 고른 결과의 범위도 밝혀야 합니다. 문서가 많을 때는 작업을 나누거나 필요한 부분을 단계적으로 읽는 방법을 함께 생각합니다.

제팔장. 긴 입력과 문서의 위치

컨텍스트 로트는 입력이 길어지면서 필요한 정보를 안정적으로 활용하기 어려워지는 현상을 다룹니다. 모든 질문의 성능이 같은 비율로 떨어지는 것은 아니므로 평균 점수와 실패한 질문을 함께 봅니다.

로스트 인 더 미들은 긴 입력 중간에 놓인 정보를 충분히 활용하지 못하는 현상입니다. 같은 문서라도 앞, 중간, 뒤에 놓았을 때 결과가 달라질 수 있습니다. 연구에서 관찰한 경향을 현재 모델에서도 직접 확인하는 과정이 필요합니다.

중요한 근거와 질문을 끝부분 가까이에 두는 배치를 시험할 수 있습니다. 어느 위치가 유리한지는 모델과 문서 길이, 방해 자료에 따라 달라집니다. 먼저 불필요한 자료를 줄이고 그다음 위치를 바꿔 보면 각 변경의 영향을 구분하기 쉽습니다.

제구장. 위치 실험의 점수 읽기

제공된 위치 실험은 정답 문서와 주제가 비슷한 방해 문서를 만들고 정답의 위치를 바꿉니다. 기본값은 방해 문서 백 개, 위치마다 다섯 번 생성입니다. 문서 수는 입력 길이에 영향을 주고 생성 횟수는 측정 비율의 해상도에 영향을 줍니다.

이 실험은 답변에 지정한 두 표현이 함께 들어 있는지 검사합니다. 두 표현을 찾으면 성공으로 셉니다. 답변이 그 표현들을 부정하거나 다른 조건을 틀려도 문자열 검사만으로는 놓칠 수 있습니다. 점수와 실제 답변을 같이 읽는 이유입니다.

다섯 번 중 한 번의 차이는 이십 퍼센트포인트입니다. 작은 시행 횟수에서 나온 비율을 일반 성능으로 확대하지 않습니다. 문서 위치, 입력 토큰 수, 생성 설정, 검사 방법을 함께 기록하면 다음 실험과 비교할 수 있습니다.

제십장. 정보를 줄이는 네 방법

컨텍스트를 관리할 때는 선별, 필요할 때 읽기, 외부 기억, 압축을 구분해 봅니다. 선별은 지금 필요한 문서를 고르는 일입니다. 필요할 때 읽기는 파일 경로나 문서 제목을 먼저 두고 다음 행동에 필요한 내용을 도구로 가져오는 방식입니다.

외부 기억은 진행 상황과 결과를 파일에 보관하고 다음 입력에는 필요한 일부를 넣습니다. 압축은 긴 문서나 기록을 짧게 바꾸어 입력에 담습니다.

어떤 방법이든 다음 판단에 필요한 정보가 빠질 가능성을 살핍니다. 원문을 보관하고 다시 찾아 읽을 수 있게 하면 누락을 복구하기 쉽습니다. 모든 정보를 매번 넣는 비용과, 필요한 정보를 다시 찾아오는 비용 사이에서 작업에 맞는 구성을 선택합니다.

제십일장. 문서 요약과 컴팩션

문서 요약은 입력 자료를 짧게 만드는 작업입니다. 컴팩션은 반복 중에 쌓인 대화와 도구 결과를 다음 작업에 필요한 기록으로 줄이는 과정입니다. 실습에서는 실패한 답변 전문 대신 발견한 위반 목록을 남깁니다.

장비 대여 규정에 기간과 승인자, 예외가 있다면 요약 뒤에도 그 조건이 남았는지 확인해야 합니다. 다음 답변의 옳고 그름을 바꾸는 숫자와 조건을 따로 보존하는 방법도 있습니다.

실습의 컴팩션 함수는 같은 위반 문자열을 중복 제거합니다. 과거에 고친 위반도 목록에는 남을 수 있습니다. 긴 대화 전체를 유지하는 방식과 비교하려면 같은 질문, 같은 생성 조건, 같은 종료 조건에서 토큰과 품질을 함께 측정합니다.

제십이장. 고정된 입력과 프리픽스 캐시

프리픽스 캐시는 여러 요청에서 동일한 입력 앞부분의 계산을 재사용하는 기능입니다. 이를 지원하고 활성화한 서버에서는 고정 지침과 공통 문서를 앞에 두는 구성이 재사용에 도움이 될 수 있습니다.

실습은 고정 지침과 문서 뒤에 질문을 두는 방식과, 질문을 앞부분에 넣는 방식의 시간을 비교합니다. 현재 로컬 챗 함수는 이전 호출의 캐시를 보관해 다음 호출로 넘기는 코드를 갖고 있지 않습니다. 따라서 이 실험에서 측정한 것은 입력 배치별 실행 시간입니다.

두 배치는 질문의 위치뿐 아니라 메시지 역할도 바꿉니다. 출력 길이나 지피유 상태도 시간에 영향을 줍니다. 캐시의 효과를 확인하려면 서버의 지원 여부와 캐시 적중량, 같은 조건에서의 지연 시간을 별도로 측정합니다.

제십삼장. 하네스에 들어가는 장치

하네스는 모델이 작업하도록 주변에서 연결하는 코드와 환경입니다. 입력을 준비하고 모델을 호출하며, 도구를 실행하고 답변을 검사합니다. 권한, 오류 처리, 작업 기록, 종료 조건도 이 구조에 포함할 수 있습니다.

미리 제공된 실행 도구와 팀에서 만든 작성 규약은 담당하는 범위가 다릅니다. 도구를 설치했다고 우리 업무의 올바른 답변 기준까지 자동으로 생기는 것은 아닙니다. 업무별 기준과 그 기준을 확인하는 방법을 연결해야 합니다.

처음에는 실제로 필요한 도구와 지침, 결과 기록부터 시작합니다. 실패한 답변을 보고 검사나 복구 장치를 추가합니다. 모델과 작업 조건이 바뀌면 기존 장치가 어떤 오류를 잡는지도 다시 확인합니다. 장치를 유지할지는 그 검사가 필요한 실패를 찾아내는지로 판단합니다.

제십사장. 가이드와 센서

가이드는 모델이 답변을 만들기 전에 읽는 작성 지침입니다. 센서는 만들어진 답변을 검사해 통과 여부와 문제점을 반환합니다. 규정의 근거를 적으라는 문장은 가이드이고, 답변에 근거 표시가 있는지 검사하는 함수는 센서입니다.

실습의 검사 함수는 패스와 이슈스를 돌려줍니다. 패스는 통과 여부, 이슈스는 발견한 위반 목록입니다. 이슈스가 구체적이면 다음 시도에 어떤 부분을 고칠지 전달하기 쉽습니다.

기록과 판정도 구분합니다. 답변과 시간을 로그에 저장하면 무엇이 일어났는지 볼 수 있습니다. 그 답변에 검사 기준을 적용하면 합격과 불합격을 판단할 수 있습니다. 루프는 이 판정을 받아 다음 행동을 정합니다.

제십오장. 센서부터 확인하기

검사 함수도 코드이므로 잘못된 판정을 할 수 있습니다. 자료에 없는 질문에는 확인이 필요하다고 답하도록 정했는데 모든 답변에 조항 번호를 요구하면 두 규칙이 충돌합니다. 올바르게 답한 모델도 같은 위반을 계속 받게 됩니다.

통과해야 할 답변과 실패해야 할 답변을 사람이 작게 만들어 센서에 넣어 봅니다. 조항을 적지 않아도 되는 예외, 문장 수의 경계, 필요한 항목이 빠진 답변을 확인합니다.

제공된 기본 센서는 문장 수, 조항 형식, 일부 존댓말 표현을 검사합니다. 엄격한 센서는 시작 문구와 끝의 근거 형식 같은 조건을 검사합니다. 이름에 엄격하다고 붙었어도 기존의 모든 검사를 그대로 포함하는지 함수 본문을 확인해야 합니다. 실제 코드에는 기본 센서의 존댓말 검사가 그대로 들어 있지 않습니다.

제십육장. 형식 통과와 사실 정확도

답변에 조항 번호가 있고 문장 수가 맞아도 내용의 숫자가 틀릴 수 있습니다. 제공된 노트북의 저장 기록에도 형식 검사에는 통과했지만 연습용 규정의 일수를 잘못 말한 사례가 있습니다. 저장 기록은 원자료의 실행 결과이며 이번 작업에서 다시 생성한 답변은 아닙니다.

형식을 검사하는 규칙과 원문에 맞는지 확인하는 기준을 구분합니다. 계산형 검사도 정답 데이터와 비교하도록 만들면 내용의 일부를 확인할 수 있습니다. 어떤 방식이 무엇을 검사하는지는 구현한 기준에 달려 있습니다.

엘엘엠 애즈 어 저지는 모델에 근거 문서와 답변을 함께 주어 내용과 조건 누락을 판정하게 하는 방식입니다. 모델 판정에도 오류가 있으므로 규칙 검사와 함께 쓰고, 중요한 사례는 원문과 대조합니다.

제십칠장. 판정 결과를 읽는 과정

모델 판정 함수는 판정 기준과 규정, 질문, 답변을 입력으로 보냅니다. 반환된 문자열에서 제이슨을 찾아 통과 여부와 위반 목록으로 사용합니다. 제이슨은 이름과 값을 일정한 구조로 표현하는 데이터 형식입니다.

제공된 함수는 제이슨을 찾지 못하거나 해석에 실패하면 판정 실패를 반환합니다. 구조를 읽는 데 성공한 뒤에도 패스가 불리언인지, 이슈스가 목록인지 같은 검사는 따로 필요합니다. 현재 예제는 내부의 모든 키와 자료형까지 확인하지 않습니다.

답변 모델과 판정 모델이 같으면 비슷한 실수를 공유할 가능성도 있습니다. 판정 결과를 기록할 때는 원문과 일치했는지, 조건을 빠뜨렸는지, 판정 형식에 문제가 있었는지를 나누어 보면 실패 원인을 찾기 쉽습니다.

제십팔장. 가이드와 재시도 비교

실습은 추가 가이드 없이 한 번 답하는 조건, 가이드를 주고 한 번 답하는 조건, 가이드와 검사 피드백으로 다시 답하는 조건을 비교합니다. 세 조건의 결과를 같은 센서로 채점합니다.

앞의 두 조건도 결과를 평가할 때 센서를 사용합니다. 차이는 생성 도중에 검사 결과를 돌려주어 다시 쓰게 하는지입니다. 또 첫 번째 조건에도 기본 시스템 지침이 들어 있습니다. 추가 작성 규약의 유무를 비교하는 구조로 읽습니다.

재시도 함수의 맥스 리트라이가 삼이면 첫 시도를 포함해 최대 세 번 생성합니다. 첫 답변이 통과하면 바로 끝납니다. 실패하면 답변과 위반 목록을 메시지에 넣고 다음 답변을 요청합니다. 통과율과 평균 생성 횟수를 함께 보면 얻은 품질과 사용한 호출 수를 비교할 수 있습니다.

제십구장. 성공과 한계와 정체와 위임

루프의 종료 이유를 성공, 한계, 정체, 위임으로 나누어 봅니다. 성공은 필요한 검사를 통과했을 때입니다. 한계는 횟수, 누적 토큰, 시간처럼 정해 둔 예산에 도달했을 때입니다.

정체는 더 시도해도 개선이 보이지 않는 상태를 뜻합니다. 실습은 직전 위반 목록과 현재 목록이 같으면 정체로 끝냅니다. 이 기준은 검사 결과의 반복을 감지합니다. 답변 내용이 전혀 바뀌지 않았는지까지 판단하는 기준은 아닙니다.

위임은 사람이 판단하거나 다른 처리 경로가 필요한 경우입니다. 제공된 코드는 정체한 질문을 따로 출력하지만 사람에게 알리거나 작업을 배정하는 동작은 담고 있지 않습니다. 결과를 분류하는 일과 실제 후속 처리의 실행을 구분합니다.

제이십장. 반복 횟수와 개선의 관계

반복 상한을 늘려도 이미 통과한 질문은 즉시 종료합니다. 그래서 상한과 실제 호출 수는 다를 수 있습니다. 상한을 하나, 둘, 셋, 다섯으로 바꾸며 통과율과 평균 시도 횟수를 함께 봅니다.

제공된 저장 기록에서는 최대 한 번일 때 팔십 퍼센트, 두 번부터 백 퍼센트가 표시됩니다. 두 번 이상에서는 평균 시도가 일 점 이 회입니다. 이 값은 작은 평가 세트의 과거 기록으로, 현재 환경의 성능을 다시 측정한 수치는 아닙니다.

정체 종료를 붙인 비교에서도 두 방식의 호출 수가 같았습니다. 이 기록으로는 절감 효과가 관찰되지 않았습니다. 다른 요청에서는 호출이 줄 수도 있고, 조금 더 시도하면 성공할 답변을 일찍 끝낼 수도 있습니다. 정체한 질문과 답변을 모아 기준이 적절했는지 확인합니다.

제이십일장. 진행 기록을 남기고 다시 시작하기

노트테이킹 실습은 질문별 답변을 프로그레스 점 제이슨 파일에 저장합니다. 다시 실행하면 기록된 질문을 건너뛰고 다음 질문을 처리합니다. 저장 기능과 컨텍스트 구성이 함께 들어 있는 예제입니다.

다음 입력에는 최근 세 답변의 앞 육십 글자만 넣습니다. 서머리라는 항목 이름을 쓰지만 실제 동작은 문자열을 앞에서 자르는 것입니다. 중요한 조건이 뒤에 있으면 잘릴 수 있습니다.

기록된 질문은 검사 실패 여부와 관계없이 건너뜁니다. 기록 파일이 깨져 해석할 수 없으면 빈 기록으로 시작합니다. 따라서 이 예제에서 확인할 것은 기록과 재시작의 기본 흐름입니다. 완료의 기준과 실패한 항목의 재처리 방식은 실제 작업에 맞춰 구분해야 합니다.

제이십이장. 요약 길이와 정보 보존

요약 실습은 원문 그대로, 글자 수의 육십 퍼센트를 목표로 한 요약, 사십 퍼센트를 목표로 한 요약을 비교합니다. 목표 글자 수와 실제 토큰 비율은 다릅니다. 모델이 목표 길이를 얼마나 따랐는지도 출력으로 확인합니다.

답변 평가는 네 질문의 키워드가 포함되었는지 셉니다. 자료에 없는 질문은 이 평가에서 제외합니다. 백 퍼센트가 표시되어도 조건과 예외, 숫자의 의미까지 전부 정확했다는 보장은 없습니다.

실습을 읽을 때는 요약된 문서의 토큰 수와 필요한 정보의 보존을 함께 봅니다. 기본 구성에서는 요약을 만드는 호출 열두 번과 답변을 만드는 호출 열두 번이 필요합니다. 입력이 짧아져도 요약 생성 자체에 드는 호출과 시간도 함께 계산해야 합니다.

제이십삼장. 질문을 나누어 답하기

서브에이전트 실습은 복합 질문을 하위 질문으로 나누고, 질문별 답변을 만든 뒤, 마지막에 합칩니다. 같은 챗 함수를 사용하면서 하위 질문마다 별도 메시지 목록을 구성합니다. 제공된 코드는 순서대로 실행합니다.

하위 질문이 엔 개라면 분해 한 번, 개별 답변 엔 번, 종합 한 번으로 총 엔 더하기 이 번 호출합니다. 각 답변에는 규정 전체를 주고 종합 단계에는 하위 답변만 줍니다. 하위 답변이 놓친 조건을 마지막 모델이 원문에서 다시 확인하기 어려운 구조입니다.

단일 호출과 비교할 때는 사실의 보존, 호출 수, 시간, 생성 설정을 함께 봅니다. 원자료의 두 방식은 종합 단계의 생성 설정도 다릅니다. 하위 작업이 서로의 결정을 알아야 하는지까지 살펴보면 작업을 나눌지 판단하는 데 도움이 됩니다.

제이십사장. 내 작업에 연결하기

선택 심화 실습은 다섯 트랙 중 두 개를 골라 목적, 바꾼 조건, 측정 결과와 해석 범위를 정리하는 구성입니다. 최종 개인 과제에서는 반복할 작업 하나를 고르고 작성 규칙 다섯 개 이상, 평가 입력 여덟 개 이상을 준비합니다.

검사 함수는 통과해야 할 답변과 실패해야 할 답변으로 먼저 확인합니다. 추가 지침 없음, 지침만 제공, 지침과 검사 피드백 제공의 세 조건을 같은 기준으로 비교합니다. 최대 생성 횟수를 하나, 둘, 셋, 다섯으로 바꾸며 통과율과 평균 시도를 기록합니다.

실패한 사례에서는 입력에 근거가 있었는지, 검사 기준이 타당했는지, 피드백으로 수정이 가능했는지 살펴봅니다. 모델을 바꾸기 전에도 이 세 질문으로 고칠 위치를 찾을 수 있습니다. 측정값과 해석을 구분해 남기면 다음 실험에서 바꿀 조건이 구체적으로 정해집니다.
